# AGENTS.md

## Project Overview

OmniSign is a Kotlin Multiplatform digital signature app (PAdES BASELINE B/B-T/B-LT/B-LTA) built on the EU DSS 6.3 library. It is a diploma thesis project — treat documentation quality and SOLID principles seriously.

## Architecture

Four Gradle modules with a strict dependency direction: `cli`/`composeApp`/`server` → `shared`.

| Module       | Role                                             | Entry point                        |
|--------------|--------------------------------------------------|------------------------------------|
| `shared`     | Multiplatform core (domain + JVM data layer)     | —                                  |
| `cli`        | Clikt-based CLI (fat JAR via Shadow)             | `cz.pizavo.omnisign.CliKt`         |
| `composeApp` | Compose Multiplatform desktop (JVM) + web (Wasm) | `cz.pizavo.omnisign.MainKt`        |
| `server`     | Ktor HTTP server                                 | `cz.pizavo.omnisign.ApplicationKt` |
| `docs`       | Docusaurus documentation site (user + developer) | `pnpm start` inside `docs/`        |

Aggregated Dokka API docs are generated via `.\gradlew.bat :dokkaGenerate` → `build/dokka/html/`.

### shared module layout (clean-architecture)

- `commonMain` — platform-agnostic domain: models, use cases, repository/port interfaces, error types, `platform/PasswordCallback.kt`, `Constants.kt`. **No DSS imports here.**
  - `domain/model/config/` — `AppConfig`, `GlobalConfig`, `ProfileConfig`, `OperationConfig`, `ResolvedConfig`, `ValidationConfig`, `AlgorithmConstraintsConfig`, `SchedulerConfig`, `RenewalJob`, `TrustedCertificateRef` (server `signing.yml` trust declarations), `TrustedCertificateType`, `CustomTrustedListConfig`, `CustomTrustedListDraft`, `CustomPkcs11Library`, `TrustedSourceId` (sealed TL-job identity key), `EtsiConstants.kt` (declares `EtsiUriHint` plus the ETSI service-type/status URI hint lists — there is no type named `EtsiConstants`), `service/` (CRL/OCSP/TSP configs), `enums/` (domain enums; only `HashAlgorithm` and `EncryptionAlgorithm` carry `dssName`).
  - `domain/model/parameters/` — `SigningParameters`, `ValidationParameters`, `ArchivingParameters`, `VisibleSignatureParameters`.
  - `domain/model/result/` — `OperationResult`, `SigningResult`, `ArchivingResult`, `AnnotatedWarning`, `RenewBatchResult`, `DocumentTimestampInfo`, plus the renewal-run family (`RenewalNeed`, `RenewalRunOutcome`, `RenewalRunRecord`, `RenewalRunJobSummary`, `RenewalRunError`, `RenewalCheckCacheEntry`, `RenewFileStatus`, `RenewJobResult`, `StalenessAlert`).
  - `domain/model/validation/` — `ValidationReport`, `ValidationResult`, `ValidationIndication`, `SignatureValidationResult`, `TimestampValidationResult`, `SignatureTrustTier`, `RevocationInfo`, `ReportExportFormat`, `ValidationReportText.kt` (`ValidationReport.toPlainText()`), `json/` (JSON report serialization).
  - `domain/model/signature/` — `CertificateInfo`, `Signature`, `TimestampInfo`, `CertificateChainLink`, `CertificateDetailSection`, `CertificateField`, `CertificateTrustSource` (sealed).
  - `domain/model/value/` — `Sensitive<T>` (+ co-located `SensitiveSerializer`), `InstantFormatter` (multiplatform date formatting), `DateFormat`, `FormatPreferences`, `DistinguishedName.kt` (`commonNameOf()`).
  - `domain/model/trust/` — `TrustScope`, `TrustedCertificate`, `ResolvedTrustAnchor`, `TrustedListLoadProgress`, `TrustedListRefreshFailure` (sealed) — app-managed trust-store models; the `TrustStore` port is in `domain/repository/`, the content-addressed `FileTrustStore` in `jvmMain/data/trust/`.
  - `domain/model/error/` — `OperationError`, `SigningError`, `ValidationError`, `ArchivingError`, `ConfigurationError`, `TrustStoreError` (sealed interfaces), all implementing the plain `LocalizableError` interface; plus `OperationErrorLocalization.kt`.
  - `domain/service/` — `AlgorithmExpirationChecker` (+ nested `AlgorithmStatus`), `CredentialStore`, `TokenService`, `SigningToken`, `TokenInfo`, `CertificateEntry`, `Pkcs11DiagnosticSnapshot`.
  - `domain/port/` — `ConfigSerializer`, `ConfigSerializerRegistry`, `SchedulerPort`, `TrustedListCompilerPort`, `ConfigArchivePort`, `RenewalCheckCache`, `RenewalRunRecordStore`, `TrustedListRefreshPort`.
  - `domain/repository/` — `SigningRepository`, `ValidationRepository`, `ArchivingRepository`, `ConfigRepository`, `CapabilitiesRepository`, `TrustStore`, `AvailableCertificateInfo`, `CertificateDiscoveryResult` (+ `TokenDiscoveryWarning`, `LockedTokenInfo`).
  - `domain/usecase/` — 16 use cases (e.g. `SignDocumentUseCase`, `ValidateDocumentUseCase`, `ManageTrustedListsUseCase`). 15 are registered in `di/AppModule.kt`; `ExportImportConfigUseCase` is the exception (see **JVM-only use cases** below).
  - `domain/model/text/` — `LocalizableText` (`Keyed(MessageKey, args)` | `Literal`), the `MessageKey` enum (125 stable, `@Serializable` identifiers), and `EnglishMessages` (the bundled English templates behind `english()`). Frontends that localize resolve the key; the CLI, server, and logs fall back to `english()`.
  - `api/model/responses/` + `api/model/requests/` — the **server↔web wire contract** (`CapabilitiesResponse`, `SigningResultMeta`, `ResolvedConfigResponse`, `ApiError`, `LoginOptionsResponse`, `SessionResponse`, `TokenResponse`, `RefreshTokenRequest`, `ExchangeCodeRequest`, …). It lives here, not in `server`, precisely so the Wasm client can deserialize what the Ktor routes serialize.
- `wasmJsMain` — HTTP-backed implementations of the *same* ports the JVM satisfies with DSS. `data/remote/` holds `RemoteSigningRepository`, `RemoteValidationRepository`, `RemoteArchivingRepository`, `RemoteConfigRepository`, and `RemoteCapabilitiesRepository`, plus `RemoteTrustStore` (implements `TrustStore`) and `RemoteConfigArchive` (implements `ConfigArchivePort`) — note those last two are *not* `*Repository`-suffixed — and `ServerErrorMapping.kt`. The `web/auth/` package holds `WebAuthApi`, `WebAuthState`, `WebSessionState`, `AuthRefreshPlugin`, `RefreshOutcome`. `di/WebDataModule.kt` wires these over **two** Ktor `HttpClient`s: a session-carrying API client (`expectSuccess = true`, attaches the `Authorization: Bearer` header, installs the auto-refresh plugin) used by every repository, and an `AUTH_HTTP_CLIENT`-qualified bare client (`expectSuccess = false`) backing `WebAuthApi` only. The `BrowserProfileSelectionStore` *interface* lives here but is bound in `composeApp/webMain/main.kt` (`LocalStorageProfileSelectionStore`), not in `WebDataModule`. Operations a browser cannot perform (`unlockToken`, `loadCertificatesFromFile`, signing with a local keystore) return a `Left` rather than throwing, so the ports stay substitutable.
- `jvmMain` — DSS-backed implementations: `data/repository/Dss*Repository.kt`, `data/service/*` (OS schedulers, PKCS#11 discovery + diagnostics, notifications, credential store, trusted list compiler, self-executable resolver), `data/trust/` (`FileTrustStore`, `CertEntry`, `CertFingerprint`, `CertRef`, `TrustStoreIndex`), `data/archive/` (`TrustArchiveEntry`, `TrustArchiveManifest`), `data/preferences/`, `data/serializer/` (Jackson-based JSON/YAML/XML config serializers), `data/util/DateExtensions.kt` (`java.util.Date` → `kotlin.time.Instant` bridging), `ades/policy/`, DI wiring (`di/JvmModule.kt`).
- DSS ↔ domain bridging uses Kotlin extension functions in `jvmMain/domain/model/config/enums/*Extension.kt` — exactly three exist: `SignatureLevelExtension`, `EncryptionAlgorithmExtension`, `AlgorithmConstraintLevelExtension` (e.g. `SignatureLevel.toDss()`). `HashAlgorithm` **and** `EncryptionAlgorithm` both carry a `dssName` property in `commonMain` because the mapping is a simple string; `EncryptionAlgorithm` has both, its `toDss()` delegating to `dssName`.

### composeApp module layout (MVVM)

The `composeApp` module delivers both the desktop (JVM) and web (Wasm) targets from a single codebase using three source sets:

- `commonMain` — shared Compose UI: `App.kt` root composable, `lumo/` design system (theme, colors, typography, custom components), `ui/layout/` (Island shell composables, dialogs), `ui/viewmodel/` (MVVM ViewModels exposing `StateFlow`), `ui/model/` (UI state data classes), `ui/platform/` (`expect` declarations for platform-specific concerns like PDF rendering, file export, cursors, theme persistence, window controls via CompositionLocals).
- `jvmMain` — desktop-specific `actual` implementations: PDFBox-based PDF renderer, `ComposePasswordCallback` (dialog-backed `PasswordCallback` + `PasswordDialogController`), JBR Custom Title Bar helper, FileKit-backed file exporter and save dialog, `WindowStateStore` (window position, persisted to `window-state.properties` in the app config dir), `UiPreferencesStore` (theme, UI language, Linux title-bar mode as JSON at `<appConfigDir>/preferences/ui.json`; the date format lives in the shared `preferences/format.json`). Entry point in `main.kt` bootstraps Koin with `appModule` + `jvmRepositoryModule` + a `PasswordCallback` binding, and also handles the headless worker modes `renew` (OS-scheduled archival renewal), `probe <libraryPath>`, and `discover-modules`.
- `webMain` — Wasm-specific `actual` implementations: MuPDF-based PDF renderer (`MuPdfShim` over the `mupdf` npm package), FileKit browser-download file export, `localStorage`-backed `UiPreferencesStore`, plus `web/auth/` (login screen, PKCE hand-off, session gate). The entry point uses `ComposeViewport` and starts Koin with `appModule` + `webDataModule(serverBaseUrl, languageProvider)` — the web target is a **full server-backed client**, with `shared/wasmJsMain`'s `Remote*` implementations satisfying the same ports the JVM satisfies with DSS, so the shared use cases run unchanged. Boot gates on auth: capabilities are read once, and when the server reports `authEnabled` nothing operational renders until `establishSession()` resolves a session; otherwise `LoginScreen` mounts. `KoinPlatform.getKoinOrNull()` remains the general mechanism for optional/absent ports, not a DSS-degradation workaround.

The **Lumo** design system is *not* a dependency: the `com.nomanr.plugin.lumo` Gradle plugin generates the theme and components into `commonMain/.../lumo/` per `lumo.properties`, and those generated sources are committed and edited in place — treat them as project code.

Key libraries: **Koin-Compose** + **Lifecycle ViewModel** (DI-aware MVVM), **FileKit** (file picker, save dialog, browser download), **Apache PDFBox** (PDF rendering, JVM only), **MuPDF** (npm, PDF rendering, Wasm only), **JBR API** (custom title bar, JVM only), **kotlin-logging** (multiplatform logging facade, backed by Logback on JVM). The web target's HTTP layer (Ktor client) is declared in `shared/wasmJsMain`, not here.

Desktop requires **JetBrains Runtime (JBR) 25** — the build fails with a descriptive error if JBR is not found. Install via IntelliJ IDEA Gradle JDK settings or download from [JBR releases](https://github.com/JetBrains/JetBrainsRuntime/releases) into `~/.jdks/`.

### server module layout

The `server` module is a Ktor/Netty HTTP server backed by the `shared` JVM data layer.

- `Application.kt` — entry point; loads `ServerConfig` via `ServerConfigLoader`, starts a Netty embedded server with an optional TLS connector (TLS 1.2/1.3, HTTP/2 ALPN). `moduleWith()` installs all plugins and Koin modules in order. `resolveExternalUrl()` derives the public base URL from the `OMNISIGN_EXTERNAL_URL` environment variable or from the server config (used to build OAuth2 redirect URIs).
- `config/` — all server-side configuration data classes:
  - `ServerConfig` — root config: `listen`, `development`, `proxy`, `operations`, `tls`, `cors`, `rateLimiting`, `maxFileSize`, `organizationName`, `auth`, `signingConfigFile`, `trustStoreDir`. (Host and port live in `ListenConfig`, not here.)
  - `AuthConfig` — SSO block: `enabled`, `providers`, `session`, plus `allowedRedirectUris` (exact-match allowlist for the browser hand-off) and `oauthStateSecret` (HMAC key protecting the OAuth2 `state`). When `null` or `enabled = false`, no JWT guard is applied to API routes.
  - `SsoProviderConfig` — sealed hierarchy; `OidcProviderConfig` (OIDC/OAuth2 authorization-code flow with optional `allowedEmailDomains` and `requiredClaims` filters) is the sole provider type.
  - `SsoProviderPreset` — built-in OIDC presets (`GOOGLE`, `MICROSOFT`, `AMAZON_COGNITO`, `KEYCLOAK`, `GITHUB`, `GITLAB`, `AUTH0`, `APPLE`, `EDUID_CZ`) that supply default discovery URLs and scope lists.
  - `SessionConfig` — JWT settings: `algorithm` (default `HS512`), `issuer` (`omnisign`), `audience` (`omnisign-api`), `tokenExpirySeconds` (300), `refreshTokenLifetimeSeconds` (2 592 000), `maxSessionSeconds` (28 800). There is deliberately **no** `secret` field — setting `secret:` in YAML fails startup; the signing secret comes from the environment only.
  - `JwtAlgorithmType` — symmetric HMAC variants (`HS256`, `HS384`, `HS512`, default `HS512`); asymmetric RS*/ES* entries are defined as future extension points but are not yet implemented.
  - `AllowedOperation` — `SIGN`, `VALIDATE`, `TIMESTAMP`. Defaults to `{VALIDATE}` alone — the only operation that exposes neither server-side signing material nor a timestamping endpoint to API callers. `SIGN` and `TIMESTAMP` are **both** opt-in, for institutional deployments where the server holds an HSM/seal certificate or fronts an institutional TSA.
  - `ListenConfig`, `TlsConfig`, `HstsConfig` (emitted by the `DefaultHeaders` plugin, not a plugin of its own), `CorsConfig`, `ProxyConfig` + `TrustedProxy`, `RateLimitConfig`, `OperationsConfig` — security and transport configurations. Config is loaded from `server.yml` via Jackson + `SsoProviderConfigDeserializer` (polymorphic deserializer for the sealed `SsoProviderConfig` hierarchy).
  - Validators run at startup and hard-fail on a bad config: `AuthConfigValidator`, `CorsConfigValidator`, `OperationsConfigValidator`, `ProxyConfigValidator`, `TransportSecurityValidator`. `SigningGatingDiagnostics` lists signing targets whose PAdES level mandates a timestamp server that is not configured.
  - Secrets: `ServerSecrets` (declared in `SecretResolver.kt` — there is no class of that name) reads the dedicated env vars `OMNISIGN_JWT_SECRET`, `OMNISIGN_TLS_KEYSTORE_PASSWORD`, `OMNISIGN_TLS_PRIVATE_KEY_PASSWORD`, `OMNISIGN_SIGNING_KEYSTORE_PASSWORD`, and `OMNISIGN_OIDC_<NAME>_CLIENT_SECRET`; `EnvVarSubstitution` (`substituteEnvVars`, `substituteTreeValues`) expands `${NAME}` placeholders in the YAML tree; `SensitiveStringJacksonDeserializer` binds them into `Sensitive<String>`; `RemovedSecretFieldHandler` rejects retired secret fields.
  - **`signing.yml`** — a separate, provider-authored, read-only signing/validation policy referenced from `server.yml` via `signingConfigFile`. `SigningConfig` is its root; `SigningConfigLoader` loads it; `ProfileSources` combines the three ways profiles may be declared (inline, files, directories). `ReadOnlyConfigRepository` exposes the resolved `AppConfig` as a `ConfigRepository`, and `TrustReconciler` reconciles the server's content-addressed trust directory against the declarative `trustedCertificates` entries.
- `auth/` — authentication domain:
  - `AuthenticatedPrincipal` — Ktor `Principal` holding `userId`, `email`, `displayName`, `providerName`, and `authTime` (the original SSO authentication instant, preserved verbatim across refreshes as the standard `auth_time` claim and used to enforce `SessionConfig.maxSessionSeconds`); embedded as JWT claims.
  - `JwtSessionService` — issues and verifies HMAC-signed JWTs (Auth0 java-jwt library). The signing secret comes **only** from the `OMNISIGN_JWT_SECRET` environment variable (via `ServerSecrets`): required when `auth.enabled = true`, and at least 64 bytes (`MIN_JWT_SECRET_BYTES`) or startup fails. With auth disabled it may be omitted, leaving the service inert (`verify` returns `null`, `issue` throws). There is no YAML source and no dev-mode auto-generation.
  - `OidcDiscoveryService` — fetches OIDC discovery documents; hard-codes GitHub's authorization and token URLs for the `GITHUB` preset.
  - `OidcUserInfoService` — calls the IdP's userinfo endpoint with the access token and maps raw JSON claims to `AuthenticatedPrincipal`.
  - `OidcAuthResult` — intermediate result holding both the mapped `AuthenticatedPrincipal` and the raw claim `JsonObject` (used by post-login filters).
  - `IdTokenVerifier` / `VerifiedIdToken` / `IdTokenVerificationException` — cryptographically verifies the IdP's `id_token` (JWKS via `jwks-rsa`) instead of trusting the UserInfo response, making the IdP's signing key the root of trust for identity assertions.
  - `PkceService` + `PkceVerifierStore` / `ExposedPkceVerifierStore` — PKCE (RFC 7636). `begin()` stores a per-flow `code_verifier` keyed by the OAuth2 `state` and returns the S256 challenge; `consume()` retrieves it for the token exchange. Required by RFC 9700 / OAuth 2.1 even for confidential clients.
  - `RefreshTokenStore` / `ExposedRefreshTokenStore` — server-side store of opaque, rotating refresh tokens issued alongside the JWT access token; backs `POST /auth/refresh`.
  - `LoginRequest` + `LoginRequestStore` / `ExposedLoginRequestStore` — park the browser's `returnTo` and `handoffChallenge` across the IdP round trip, keyed by the OAuth2 `state`.
  - `HandoffCodeStore` / `ExposedHandoffCodeStore` — single-use, PKCE-bound hand-off code (30 s TTL) redeemed by `POST /auth/exchange`, so the SPA never has to read tokens out of a URL.
  - `RedirectUriFilter` — `isRedirectUriAllowed()` exact-matches the requested `returnTo` against `auth.allowedRedirectUris`.
  - `RefreshCookie` — `REFRESH_TOKEN_COOKIE` helpers (`setRefreshCookie` / `clearRefreshCookie` / `refreshCookie()`); the cookie is scoped to `/auth/refresh`.
  - `SessionsDbPath` — resolves the SQLite file (`<appDataDir>/omnisign/sessions.db`); the `omnisign.sessions.dbFile` system property overrides it. Both Exposed-backed stores above persist here.
  - `EmailDomainFilter` — `isEmailDomainAllowed()` checks the user's email domain against `OidcProviderConfig.allowedEmailDomains`.
  - `OidcClaimsFilter` — `areRequiredClaimsSatisfied()` validates raw IdP claims against `OidcProviderConfig.requiredClaims` (supports single-valued and multi-valued array claims).
  - `ServerPasswordCallback` — `PasswordCallback` implementation that always returns `null` (the server cannot prompt interactively).
- `api/routes/` — one file per route group, all mounted under `/api/v1` **except `AuthRoutes`, which is mounted at `/auth`**:
  - `AuthRoutes` — `/auth/**`: `GET /login` (provider list), `GET /redirect/{name}` (OIDC initiation; accepts `returnTo` + `handoffChallenge`), `GET /callback/{name}` (OIDC exchange; either returns `TokenResponse` JSON or `302`s back to an allowlisted `returnTo` carrying a hand-off code), `GET /session` (**the one auth route that requires a Bearer JWT**), `POST /refresh`, `POST /exchange` (redeems the single-use, PKCE-bound hand-off code), `POST /logout`.
  - `SigningRoutes`, `ValidationRoutes`, `TimestampRoutes`, `CertificateRoutes`, `SystemRoutes` (health + capabilities).
  - `ConfigRoutes` — `GET /config/global`, `/config/profiles`, `/config/profiles/{name}`, `/config/resolved`, `/config/trusted-certificates`, and `/config/export` (whole configuration as a ZIP).
- **Wire DTOs live in `shared`, not in `server`.** The response classes the web client also has to deserialize are in `shared/commonMain/.../api/model/responses/`: `CapabilitiesResponse`, `SigningResultMeta`, `TimestampResultMeta`, `GlobalConfigResponse`, `ProfileConfigResponse`, `ResolvedConfigResponse`, `TimestampServerSummary`, `TrustedCertificateResponse`, plus `ApiError`, `LoginOptionsResponse`, `SessionResponse`, and `TokenResponse`. Request DTOs sit alongside in `shared/commonMain/.../api/model/requests/`: `RefreshTokenRequest`, `ExchangeCodeRequest`. That shared package *is* the server↔web contract — change it and both sides move together.
- `server`'s own `api/model/` now holds only `responses/HealthResponse` and `FilePartData`; there is **no** `server/.../api/model/requests/` package.
- `api/exception/` — `OperationException` (wraps `OperationError` for `StatusPages` handling), `FileTooLargeException`, `MultipleFilePartsException`.
- `api/RouteUtils.kt` — shared route helpers: `requireOperation`, `collectParts`, `deleteFileParts`, `extractTextField`, `parseEnumSetField` (`rateLimitedIf` lives in `plugins/RateLimit.kt`, not here). `api/RequestLanguage.kt` reads the caller's `Accept-Language` and feeds `ValidationParameters.language`, so DSS validation reports are localized **per request**.
- `plugins/` — one file per Ktor plugin installation: `Authentication`, `Routing`, `Serialization`, `StatusPages`, `CallId`, `CallLogging`, `Cors`, `DefaultHeaders`, `ForwardedHeaders`, `HttpsRedirect`, `RateLimit`, `AutoHeadResponse`. (There is **no** compression plugin or `CompressionConfig`.)
- `di/ServerModule.kt` — server Koin module; provides `ServerConfig`, `ServerConfigLoader`, `ServerSecrets`, `PasswordCallback` (always null), `CoroutineContext` (IO), `HttpClient` (CIO, JSON content-negotiation, `HttpTimeout` 10 s request / 5 s connect / 10 s socket), `JwtSessionService`, `OidcDiscoveryService`, `OidcUserInfoService`, `IdTokenVerifier`, `PkceService`, `NonceManager` (`StatelessHmacNonceManager`, keyed from `auth.oauthStateSecret`), `ConfigRepository` (`ReadOnlyConfigRepository`), `TrustStore` (`FileTrustStore`), `TrustReconciler`, the four Exposed stores (PKCE verifiers, refresh tokens, login requests, hand-off codes), and a lazy `Database` singleton (`Database.connect("jdbc:sqlite:…")` rooted at `sessionsDbFile`, `PRAGMA busy_timeout = 5000`).

Key libraries: **Ktor** (Netty engine, server framework), **Auth0 java-jwt** (JWT signing/verification), **jwks-rsa** (IdP JWKS fetch for `IdTokenVerifier`), **Exposed** + **sqlite-jdbc** (PKCE verifiers and refresh tokens in `sessions.db`), **Ktor client CIO** (OIDC discovery and userinfo HTTP calls), **kotlin-logging** (Logback-backed).

### Key patterns

- **Error handling**: `OperationResult<T>` = `Arrow Either<OperationError, T>`. All errors are sealed interfaces under `domain/model/error/`. Use `.left()` / `.right()`, never throw for expected failures.
- **DI**: Koin is the **sole** dependency-injection mechanism — use it everywhere possible. Register all services, repositories, use cases, factories, and helpers as Koin definitions (`single`, `factory`, `scoped`). Kotlin `object` declarations are permitted **only** when Koin is technically impossible or nonsensical (e.g., Compose `*Defaults` objects that supply default parameter values, `LumoTheme` accessor, multiplatform `expect`/`actual` utilities that must be resolved at compile time, or `companion object` blocks holding constants/loggers/factory methods). When adding a new class, default to a Koin-managed definition; justify with a comment in the module file if an `object` is truly required. Common use cases are registered in `shared/commonMain/.../di/AppModule.kt`; JVM repository bindings in `shared/jvmMain/.../di/JvmModule.kt`. Each UI module bootstraps Koin in its `main()` and must provide a `PasswordCallback` implementation.
- **Config resolution**: Three-layer merge (global → profile → operation overrides) in `ResolvedConfig.resolve()`. Config is persisted as JSON via `FileConfigRepository` at `~/.config/omnisign/` (Linux), `~/Library/Application Support/omnisign/` (macOS), or `%APPDATA%/omnisign/` (Windows).
- **DSS infrastructure**: `DssServiceFactory` centralises TSP sources, certificate verifiers, and TL validation jobs — injected into all `Dss*Repository` classes. Run `.\gradlew.bat :shared:updateLotlKeystore` to refresh the bundled EU LOTL keystore when the EC rotates its signing keys.
- **Sensitive values**: `Sensitive<T>` (`domain/model/value/Sensitive.kt`) is a `data class` whose `toString()` returns `***`. Wrap credentials with it to prevent accidental log/debug leaks. Serialization is intentionally blocked (`SensitiveSerializer` throws on both `serialize` and `deserialize`). It is deliberately **not** a `@JvmInline value class`: as a generic type argument it erases to the boxed form on the JVM anyway, and an inline value class trips a Kotlin reflection bug where `callBy` cannot invoke a primary constructor that mixes default-valued parameters with a value-class parameter — the path Jackson's `KotlinModule` takes when constructing server config classes such as `TlsConfig`.
- **JVM-only use cases**: `ExportImportConfigUseCase` lives in `commonMain` but depends on Jackson serializers, so it is registered in `jvmRepositoryModule`, not `appModule`. Three more are located in `jvmMain` and registered there: `ConfigArchiveUseCase` (ZIP export archives pairing serialized config with its trusted certificates; bound to `ConfigArchivePort`), `RenewBatchUseCase` (DSS-backed archiving), and `MigrateTrustedCertificatesUseCase` (moves inline certificates into the file-backed trust store).
- **DSS warning pipeline**: DSS diagnostics are captured via two mechanisms — `CollectingStatusAlert` (wired into the `CertificateVerifier`) and `DssLogCapture` (a Logback appender attached to the `eu.europa.esig` parent logger during operations). Raw warnings are then classified by `DssWarningSanitizer` into `WarningCategory` buckets and emitted as user-friendly summaries. `TspErrorDetector` extracts RFC 3161 `PKIFailureInfo` codes from TSP exceptions.
- **composeApp MVVM**: ViewModels in `composeApp/commonMain` extend `ViewModel` (Lifecycle) and expose `StateFlow<UiState>`. Despite the `koin-compose-viewmodel` dependency, **`koinViewModel()` is not used anywhere** — `ui/layout/IslandLayout.kt` constructs each ViewModel by hand inside `remember { runCatching { KoinPlatform.getKoinOrNull() … } }`, resolving constructor dependencies via `koin.get()`/`koin.getOrNull()` and falling back to a `null` ViewModel (and a stub `MutableStateFlow`) when a definition is absent — which is how the web target copes with ports it cannot bind. Heavy work (signing, certificate discovery) runs on a constructor-parameter `CoroutineDispatcher` defaulting to `Dispatchers.Default`, overridden in tests. See `SigningViewModel` for the canonical pattern. Shared cross-ViewModel logic (e.g., renewal job offers) is factored into plain classes like `RenewalJobAssigner`.
- **Server authentication flow**: `configureAuthentication()` registers a `jwt-api` Bearer provider (always installed, even when auth is disabled) and one `oidc-{name}` OAuth2 provider per `OidcProviderConfig`, each wired to the injected `NonceManager` (`StatelessHmacNonceManager`) so the OAuth2 `state` is HMAC-verified on callback — Ktor's default `GenerateOnlyNonceManager` would accept any state. `configureRouting()` wraps all operational routes in `authenticate(jwt-api)` when `auth.enabled = true`; health and capabilities stay public, as do the `/auth/**` routes **except `GET /auth/session`**, which requires a valid Bearer JWT. `PkceService.begin()` (S256 challenge, verifier stored by `state`) runs in the `authorizeUrlInterceptor` and `consume()` in the `providerLookup`, both in `plugins/Authentication.kt` rather than the route handlers. The callback verifies the returned `id_token` with `IdTokenVerifier` and rejects a mismatch between its `sub` and the UserInfo `sub` (`401 ID_TOKEN_SUB_MISMATCH`). Post-login checks (`isEmailDomainAllowed`, `areRequiredClaimsSatisfied`) then run before a JWT access token and an opaque, rotating refresh token are issued.
- **Server allowed operations**: only `VALIDATE` is enabled by default (`OperationsConfig.allowed`); `SIGN` and `TIMESTAMP` are both opt-in. `AllowedOperation.SIGN` additionally triggers a startup warning when enabled without `auth.enabled = true` (`Application.kt`). Each route group checks its corresponding `AllowedOperation` at request time.
- **Server rate limiting**: Two independent token-bucket zones — `auth` (default 20 req/60 s per IP) and `api` (default 200 req/60 s per IP). In `proxyMode`, the real client IP is resolved via `X-Forwarded-For` by the `ForwardedHeaders` plugin before rate limiting evaluates it.

## Build & Run

Requires **JDK 25+**. All JVM tasks need `--enable-native-access=ALL-UNNAMED` (already configured in `gradle.properties` and build scripts).

```powershell
.\gradlew.bat :cli:shadowJar                          # CLI fat JAR → cli/build/libs/omnisign-*.jar
.\gradlew.bat :cli:run --args="--help"                 # Run CLI directly
.\gradlew.bat :cli:jpackage                            # Native installer for current OS (MSI/DEB/RPM/DMG)
.\gradlew.bat :composeApp:run                          # Desktop app (requires JBR 25)
.\gradlew.bat :server:run                              # Ktor server
.\gradlew.bat :composeApp:wasmJsBrowserDevelopmentRun  # Web (Wasm)
```

## Testing

Framework: **Kotest 6** (FunSpec style) + **MockK** + **Arrow Kotest matchers** (`shouldBeLeft()` / `shouldBeRight()`). Tests live in `src/jvmTest` (shared, composeApp), `src/test` (cli, server), plus `src/commonTest` (`shared` has ~20 specs there, run as part of `:shared:jvmTest`).

```powershell
.\gradlew.bat :shared:jvmTest
.\gradlew.bat :cli:test
.\gradlew.bat :server:test
.\gradlew.bat :composeApp:jvmTest
```

`:shared:jvmTest`, `:cli:test`, and `:server:test` add `-XX:+EnableDynamicAgentLoading -Xshare:off --enable-native-access=ALL-UNNAMED` (plus smartcardio module/opens flags); `:composeApp:jvmTest` sets only `useJUnitPlatform()`. Decoroutinator (readable coroutine stack traces) is applied as a Gradle plugin in `shared` and `composeApp`, while `cli` and `server` pull the `stacktrace-decoroutinator-jvm` runtime artifact instead.

**Gradle's `--tests` filter does not work with this Kotest setup** — it reports "No tests found". Run the whole module task and read `build/test-results/<task>/TEST-*.xml` for per-spec results.

CLI command tests use the Kotest `KoinExtension` with `KoinLifecycleMode.Test` to supply mocked dependencies per spec (see `cli/src/test/.../commands/SignTest.kt` for the pattern).

composeApp ViewModel tests use `StandardTestDispatcher` + `runTest` with `Dispatchers.setMain`/`resetMain`, injecting mocked use cases directly (no Koin). See `composeApp/src/jvmTest/.../ui/viewmodel/SigningViewModelTest.kt` for the pattern.

## Coding Conventions

- Every class, interface, and function **must** have a KDoc comment.
- Do **not** add inline comments unless specifically asked.
- Do **not** generate Markdown files unless specifically asked.
- **One top-level declaration per file.** Each `.kt` file may contain at most one top-level class, interface, enum, `object`, or sealed hierarchy. Nested/inner classes inside that declaration are fine. Extension functions related to the declaration may coexist in the same file. However, no additional standalone type declarations are allowed (e.g., do **not** put a data class and an enum in the same file, or two data classes in the same file). Name the file after the declaration it contains.
- **Prefer Koin for all dependency wiring.** Never introduce a Kotlin `object` singleton for a service, repository, use case, or helper that could be a Koin-managed `single`/`factory`. Kotlin `object` is acceptable only for Compose component defaults (`*Defaults`), theme accessors (`LumoTheme`), compile-time `expect`/`actual` utilities, and `companion object` blocks (constants, loggers, factory methods).
- **Prefer Kotlin APIs over Java ones.** Always use a Kotlin standard library and multiplatform types when an equivalent exists — e.g. `kotlin.uuid.Uuid` instead of `java.util.UUID`, `kotlin.time.Instant` / `kotlin.time.Duration` instead of `java.time.*`, `kotlin.io.path.*` extensions instead of raw `java.nio.file.*` calls. Fall back to a Java API only when no Kotlin equivalent exists or when bridging with a Java library that requires it (e.g., DSS), and isolate that bridge in `jvmMain`.
- Domain enums live in `commonMain` and are mapped to DSS by extension functions in `jvmMain/.../enums/*Extension.kt`. Only `HashAlgorithm` and `EncryptionAlgorithm` carry a `dssName` property directly, where the mapping is a plain string.
- Serializable config models use `kotlinx.serialization`. Jackson serializers (`data/serializer/`) handle YAML/XML export/import.
- CLI commands extend `CliktCommand` and obtain dependencies via `KoinComponent.inject()`. Shared options are grouped in `OperationConfigOptions`.
- The `PasswordCallback` interface is the platform boundary — CLI uses terminal input, desktop uses a dialog (`ComposePasswordCallback`), server returns `null` (it cannot prompt interactively).
