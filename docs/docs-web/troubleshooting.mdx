# Troubleshooting

Almost everything the web app does beyond opening a PDF needs the server, and its network layer is
deliberately thin: it retries only once, and only to refresh an expired session token; it has no
offline indicator, and every kind of network failure looks the same. This page explains how to tell
them apart.

## The page is blank or never finishes loading

The frontend needs **WebAssembly GC**, which arrived in Chrome/Edge 119, Firefox 120, and Safari 18.2.
An older browser loads the page and then fails to start the app. Check your browser version first; the
browser console will usually show a WebAssembly error.

## The Sign or Timestamp button is missing

Either the server does not permit that operation, or the app could not reach the server at startup.
Signing and timestamping are opt-in server-side and validation is on by default, so a deployment may
legitimately offer validation only — ask the administrator to enable it. But the capability check also
**fails closed**: if it cannot reach the server, it assumes *no* operation is permitted and hides every
button, so a missing button can equally mean the server is unreachable. Rule of thumb — if *all* the
operation buttons (and the **Signature** panel) are gone, suspect connectivity first; if only one is
missing, suspect operation gating. See [Server → Operation gating](/server/security#operation-gating).

The **Signature** panel likewise disappears when the server does not permit `VALIDATE` — or cannot be
reached.

## The buttons are there, but an operation fails

The capability check runs once at startup and fails closed, so if the buttons *are* present the server
was reachable when the app loaded. A later failure therefore means the server has since gone down, the
request was rejected, or your session ended — see the messages below.

## "Remote signing failed" / "Remote validation failed"

These generic messages cover every network-level failure, and they are deliberately bare: the client
reads only the server's error *code* and discards its message and details, so no HTTP status, JSON
envelope, or DSS reason is ever shown in the UI. Only three server rejections get a specific message
instead (invalid configuration, timestamping not allowed, certificate not allowed). In order of
likelihood:

1. **The server is unreachable** — it is down, or the address is wrong. See
   [Deployment → Connecting to a server](deployment.mdx#connecting-to-a-server).
2. **CORS is blocking the request.** The browser refuses to let the page talk to a different origin
   unless the server allows it. The server's `cors.allowedOrigins` must include the origin serving the
   web bundle. See [Server → CORS](/server/security#cors).
3. **Your session ended.** On an auth-enabled server, an expired session makes operations come back
   `401`. The app tries to refresh silently and retries the request once; only if the server rejects
   the refresh does it drop back to the sign-in screen — in place, with no page reload. If the server
   was merely unreachable, you stay signed in and see an ordinary failure instead. See
   [Deployment → Authentication](deployment.mdx#authentication).
4. **The server refused the upload.** A PDF above the server's `maxFileSize` (100 MB by default)
   comes back `413`, and too many requests from one address come back `429`. Both look like any other
   failure in the app.
5. **The operation genuinely failed** — an unreachable timestamp authority, an expired server
   certificate, a malformed PDF. The reason stays in the server's log; the browser shows only the
   generic message.

Open the browser's developer console: it shows the actual HTTP status, which separates a failed
preflight (CORS) from a `401` (authentication) from a connection refused (server down).

Only the **Signature** panel offers a **Retry** button. Everywhere else, close the dialog and try
again.

## Signing reports "No tokens detected"

This is a server-side problem, not a browser one: the server has no usable signing certificate. Its
keystore is missing, unreadable, or empty. The banner's advice about inserting a smart card is written
for the desktop app and does not apply here. See
[Server → Configuration](/server/configuration#operations).

## The signed document did not reopen after I saved it

On Firefox and Safari the signed file is delivered as an ordinary **download**, and the page is not
allowed to learn where it went — so the viewer cannot reload it. Open the downloaded file yourself.
Chromium browsers show a real *Save As* dialog and reopen the result automatically. See
[Signing → Save the signed document](guides/signing.mdx#6-save-the-signed-document).

## I cannot add a certificate to the trusted list

Trust belongs to the server and is read-only over the API, so the *add to trusted* action from the
validation report, the trusted-certificate add form, and the Trusted List builder are all absent. An
administrator adds anchors to the server's configuration. See
[Validating signatures](guides/validation.mdx#4-inspect-and-export-certificates).

## Where the logs are

There are none. The Help panel's **Support** section — log export and debug-logging toggles — is
desktop-only, because a browser has no local log files. Use the browser's developer console for
client-side errors, and ask the administrator for the server's log for anything else. Server-side
troubleshooting lives in [Server → Deployment](/server/deployment).
