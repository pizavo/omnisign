# Deployment

This page is for whoever puts the web frontend on a server. Users need none of it — start at
[OmniSign Web](index.mdx).

The frontend is a **static bundle**: HTML, JavaScript, and a WebAssembly module. It has no backend of
its own. Every operation it performs is an HTTP call to an [OmniSign Server](/server/), so a
deployment is always two pieces — the static files, and the API they point at.

`web-dist.zip` asset on the GitHub release.

:::note[Same-origin hosting]
The OmniSign Server serves only `/api/v1/**` and `/auth/**` — it has no static-file route. To put the
bundle and the API on one origin, front both with a reverse proxy that serves the static files and
passes those two prefixes through.
:::

## Connecting to a server

The bundle is static, so the API it talks to is chosen at **deploy time**, not compiled in. On startup
the app fetches an optional **`web-config.json`** served next to `index.html`:

```json
{
  "serverUrl": "https://omnisign.example.com:18443",
  "organizationName": "University of Ostrava"
}
```

Both keys are optional:

- **`serverUrl`** — the origin API requests go to. When omitted or blank, requests go to the **same
  origin** that served the bundle, which is the topology where one OmniSign Server hosts both the web
  files and the API. Point it at a separate host and [CORS](#cors) must then allow the web origin.
- **`organizationName`** — a branding label, see [Branding](#branding).

The file is fetched with a **3-second timeout**. If it is missing, blank, or unreachable, the app falls
back to the server URL baked in at build time (`OMNISIGN_SERVER_URL`; empty means same origin). A
**present but malformed** `web-config.json` is not silently ignored: the app logs a console warning and
uses the build-time fallback, so a deploy typo stays visible.

Retargeting a deployed bundle is therefore just editing `web-config.json` — no rebuild.

## CORS

If the web bundle and the API are on different origins, the browser will refuse the requests unless the
server opts in. Add the web origin to the server's `cors.allowedOrigins`:

```yaml
# server.yml
cors:
  allowedOrigins: ["https://sign.example.org"]
```

A blocked preflight surfaces in the app as an ordinary "remote operation failed" error, so check the
browser console when diagnosing. See [Server → CORS](/server/security#cors).

## Authentication

When the server's [`auth:` block](/server/authentication) is enabled, the web app gates its **whole**
UI behind sign-in. At startup it reads the public `GET /api/v1/capabilities`, sees `authEnabled`, and
shows a login screen listing the server's OIDC providers instead of the app — nothing operational
renders until the user has a session. With authentication disabled the app loads straight into the UI,
as it always has.

### How sign-in works

The browser never handles the identity provider's tokens itself. Clicking a provider sends it to the
server's `/auth/redirect/{provider}`, which bounces to the IdP (Google, Microsoft Entra, eduID.cz, …);
once the user authenticates, the server redirects back to the app with a **one-time hand-off code**,
which the app exchanges for a short-lived session. The access token lives only in the tab's memory,
and an `HttpOnly` refresh cookie scoped to `/auth/refresh` lets a page reload resume the session
without another trip to the IdP. Closing the **browser** ends the session: the refresh cookie carries
no `Max-Age`, so it is dropped when the browser exits. Closing just the tab does not — reopening the
app in the same browser resumes silently from the cookie. The server caps a session at
`auth.session.maxSessionSeconds` (8 hours by default) regardless.

Two server settings make this work:

- **`auth.allowedRedirectUris`** must list the exact URL the web app is served from — scheme, host,
  and path, **including the trailing slash**. The app asks to return to its own `origin + pathname`
  (e.g. `https://sign.example.org/`), and the server matches it character-for-character:
  `https://sign.example.org` without the slash will **not** match. The match is deliberately exact
  rather than a prefix, because whatever this permits receives a login credential.
- **`cors.allowCredentials: true`** is needed when the web app and the API are on **different origins
  of the same site** (e.g. `app.example.org` + `api.example.org`, or one host with the API on a second
  port), so the browser will send the refresh cookie to `/auth/refresh`. The cookie is `SameSite=Lax`,
  so on a genuinely **cross-site** split — different registrable domains — it is withheld regardless of
  CORS; the app still works, it just re-authenticates through the identity provider on every page load
  (a redirect the user does not see). The server rejects it in combination with
  `cors.allowedOrigins: ["*"]` — list the app's origin explicitly. On a same-origin deployment you do
  not need it.

## Choosing what users can do

The frontend adapts to the server. At startup it reads `GET /api/v1/capabilities` and hides the
affordances for operations the server does not expose:

| `operations.allowed` | What disappears from the UI                                     |
|----------------------|------------------------------------------------------------------|
| without `VALIDATE`   | The Signature panel and its left-edge icon                      |
| without `SIGN`       | The Sign toolbar button                                          |
| without `TIMESTAMP`  | The Timestamp toolbar button, and the signing dialog's timestamp checkboxes |

`VALIDATE` is enabled by default; `SIGN` and `TIMESTAMP` are opt-in. See
[Server → Operation gating](/server/security#operation-gating).

If the capabilities request fails, the app **fails closed**: every flag stays denied, so the Sign and
Timestamp buttons and the Signature panel are all hidden and the deployment looks empty rather than
broken. Do not rely on button visibility as an access control either way; the server enforces the
gating on every request.

## Branding

Two independent labels can prefix the product name, and both are optional:

- **`organizationName` in `web-config.json`** — set by whoever deploys the *web bundle*.
- **[`organizationName` in `server.yml`](/server/configuration#organizationname)** — set by whoever
  operates the *server*, and returned from `/api/v1/capabilities`.

They appear in the browser-tab title, the toolbar, and the empty-state mark. When both are set they are
combined, most-local first, always ending in `OmniSign` — for example
`University of Ostrava · Microsoft · OmniSign`. With neither set, the app is simply *OmniSign*.

## Checklist

1. Build the bundle and copy `productionExecutable/` to the web root.
2. Write `web-config.json` next to `index.html` if the API is on another origin, or if you want a
   branding label.
3. Allow the web origin in the server's `cors.allowedOrigins`.
4. Confirm the server's `operations.allowed` matches what you want users to see.
5. If the server enables authentication, list the web app's exact URL (with its trailing slash) in
   `auth.allowedRedirectUris`, and set `cors.allowCredentials: true` when the app and API are on
   different origins.
