# Configuration (`server.yml`)

`server.yml` controls how the server is **exposed and secured** — the network bind, TLS, CORS,
reverse proxy, rate limiting, authentication, and which operations are allowed. How the server
*signs and validates* lives in a separate [`signing.yml`](signing-policy) policy file.

A fully-commented template ships as **`server.example.yml`** (in `server/src/main/resources/`, and
inside the JAR — extract with `jar xf <jar> server.example.yml`). Copy it to `server.yml` and edit.

## How the configuration is loaded {/* #resolution-order */}

The server resolves its config file from the first source that exists, in order:

1. `--config <path>` on the command line.
2. The `OMNISIGN_SERVER_CONFIG` environment variable.
3. `server.yml` in the current working directory.
4. **Built-in defaults** — used only as a last resort, with a warning. The defaults do **not**
   start a usable server: a `cors:` block is required, and a non-loopback host requires `tls:` or
   `proxy:`. There is **no classpath fallback** — the bundled `server.example.yml` is documentation
   only and is never auto-loaded.

Three parsing rules protect you from silent misconfiguration:

- **Unknown keys fail startup.** A typo like `auth: { enable: true }` (missing `d`) or
  `tls: { keystorePat: … }` would otherwise silently disable a defense; instead the server refuses
  to start and names the offending key.
- **Values must say what they mean.** The file is read as YAML 1.2, so `true` and `false` are the
  booleans, and `yes`, `no`, `on`, or `off` on a boolean key fails startup. `~` and an empty value mean
  null, which a number or boolean key refuses rather than reading as `0` or `false`: a blank `port:`
  cannot bind a random port. A second document after `---` also fails startup rather than being
  ignored.
- **`${VAR}` substitution** — any string *value* may reference an environment variable as `${NAME}`
  (`[A-Z_][A-Z0-9_]*`), expanded at load. Keys and comments are never substituted; a referenced-but-
  unset variable fails startup. Use this for non-secret values like an external URL — and for
  `auth.oauthStateSecret`, the one secret the schema expects as a `${VAR}` reference rather than a
  direct environment read. A name that starts with `OMNISIGN_` can also be set in a file, like the
  secrets below (see [Secrets in files](#secrets-in-files)).

## Secrets {/* #secrets */}

Secrets never come from YAML. Setting any of them there fails startup with an error naming the
variable to use instead, because a YAML file ends up in backups, logs, images, and screen-shares.
Each secret `<NAME>` in the table below is read from the environment variable `<NAME>`, from the file
that `<NAME>_FILE` names, or from the systemd credential `<NAME>` (see
[Secrets in files](#secrets-in-files)). The one exception is `auth.oauthStateSecret`, which is a real
YAML field that must carry a `${VAR}` reference rather than a literal.

| Environment variable                | Purpose                                                            |
|-------------------------------------|--------------------------------------------------------------------|
| `OMNISIGN_JWT_SECRET`               | HMAC signing secret for session JWTs (required when auth enabled; ≥64 bytes) |
| `OMNISIGN_OAUTH_NONCE_SECRET`       | HMAC key protecting the OAuth2 `state` parameter against login CSRF. Required whenever OIDC providers are configured; ≥64 bytes. Referenced *from* YAML as `auth.oauthStateSecret: "${OMNISIGN_OAUTH_NONCE_SECRET}"` |
| `OMNISIGN_OIDC_<NAME>_CLIENT_SECRET`| Per-OIDC-provider `client_secret` (`<NAME>` = provider `name`, uppercased, non-alphanumerics → `_`) |
| `OMNISIGN_TLS_KEYSTORE_PASSWORD`    | TLS keystore password (required when `tls:` is set)                |
| `OMNISIGN_TLS_PRIVATE_KEY_PASSWORD` | TLS private-key password (optional; falls back to the keystore password) |
| `OMNISIGN_SIGNING_KEYSTORE_PASSWORD`| File signing-keystore password (required when `operations.signingKeystorePath` is set with `SIGN` enabled) |

`OMNISIGN_EXTERNAL_URL` is not a secret, but belongs alongside them: it sets the public base URL used
to build OAuth2 redirect URIs, and is recommended in production.

The TSA password used by [`signing.yml`](signing-policy) is also supplied from the environment, via a
`${VAR}` reference in that file.

### Secrets in files {/* #secrets-in-files */}

On Linux and macOS, a secret can be kept in a file instead: set the variable's name followed by
`_FILE` to the file's path. This suits the secrets Docker and Kubernetes mount into a container as
files, and it keeps the secret out of the process environment, which `docker inspect` shows and every
child process inherits.

```bash
export OMNISIGN_JWT_SECRET_FILE=/run/secrets/jwt-secret
```

Under systemd, a credential named like the variable is read as well, such as one the unit loads with
`LoadCredential=OMNISIGN_JWT_SECRET:/etc/omnisign/credentials/jwt-secret` (see
[Deployment → Bare-metal service](deployment#bare-metal-service)).

A `${NAME}` placeholder whose name starts with `OMNISIGN_` is read the same way, so
`auth.oauthStateSecret` and the TSA password in `signing.yml` can come from files too. Any other name
is read from its variable only, so a variable that another program reads, such as `SSL_CERT_FILE`,
keeps its meaning.

A secret file is read only when all of these hold:

- It is a regular file of at most 64 KiB. A link is followed, and the file it leads to is checked.
- It is owned by the user the server runs as and has mode `0600` or stricter, or it is owned by
  `root` and has mode `0640` or stricter, which lets one group read it.
- It is not on an overlay file system, where a container keeps the files of its image and those
  written into it. Mount the secret when the container starts instead.

Otherwise the server does not start and says what to change, such as `chmod 600 <file>`. One line
break at the end of the file is dropped, and an empty file is refused.

Set each secret in one place only. When more than one of the variable, the `_FILE` variable and the
systemd credential is set, the server does not start instead of choosing one; an empty variable does
not count. Windows takes only the variable, because there the owner of a file and who may read it
cannot be checked this way.

Kubernetes and Docker swarm let every user read a mounted secret unless told otherwise, and the
server refuses such a file. Set the owner and mode a mounted secret gets:

- **Kubernetes** mounts the files of a secret volume as owned by `root` with mode `0644`. Set the
  volume's `defaultMode: 0440`, and set the pod's `securityContext.fsGroup`: the files then belong to
  that group, and the server runs as a member of it.
- **Docker swarm** mounts a secret with mode `0444`. Give it `mode: 0400` with `uid` set to the user
  the server runs as, or `mode: 0440` with `gid` set to its group.
- **Docker Compose** without swarm mounts the secret's file from the host as it is, and ignores
  `uid`, `gid` and `mode`. Make the user the server runs as the file's owner on the host, and give the
  file mode `0600`.

[Deployment → Docker](deployment#docker) shows how to find the user and group the image runs as.

## File reference

Every block is optional unless noted. The most security-relevant blocks are detailed on the
[Security](security) and [Authentication](authentication) pages; this is the field reference.

### `listen`

Network bind. Defaults to loopback so a fresh install is reachable only from the same machine.

```yaml
listen:
  host: "127.0.0.1"   # 0.0.0.0 for all interfaces (then tls: or proxy: is required)
  port: 18080
```

### `development`

`true` enables Ktor development mode (auto-reload, verbose error pages that echo internal details).
**Refuses to start on a non-loopback host.** Must be `false` in production.

### `operations`

Which operations the API exposes, and (for signing) which certificate aliases are eligible. Defaults
to `VALIDATE` only; `SIGN` and `TIMESTAMP` are opt-in. See [Security → Operation gating](security#operation-gating).

```yaml
operations:
  allowed: [VALIDATE]          # add SIGN and/or TIMESTAMP to enable them
  # certificateAliases: ["University Seal-1f3a@pkcs11-5A3C0F12"]   # restrict signing to these aliases
  # signingKeystorePath: "/etc/omnisign/signing.p12"   # sign from a PKCS#12 file (see below)
```

`certificateAliases` takes the aliases exactly as
[`GET /api/v1/certificates`](/server/api/list-certificates) lists them, in the form
`<common name>-<serial number in hex>@<source id>`. A label you gave the key yourself never matches.
With `certificateAliases` set, a sign request that names no certificate signs with the only listed
alias. When the list holds several, the request has to name one, and is otherwise rejected with
`400 MISSING_CERTIFICATE_ALIAS`.

`signingKeystorePath` lets the server sign from a PKCS#12 (`.p12`/`.pfx`) **file** instead of a
PKCS#11 token/HSM. When set (with `SIGN` enabled), every sign request signs from this keystore, and
`certificateAliases` selects the entry within it — a request omitting the alias uses the only allowed
alias, or the keystore's first key when `certificateAliases` isn't set. Its password comes from
`OMNISIGN_SIGNING_KEYSTORE_PASSWORD` (see [Secrets](#secrets)).
Setting the path without `SIGN` in `allowed`, or pointing it at a missing file, is rejected at
startup. Leave it unset for a PKCS#11/HSM-backed deployment. The keystore's certificate(s) are also
surfaced through [`GET /api/v1/certificates`](/server/api/list-certificates) so remote clients can pick the
server's signing identity.

### `proxy`

Reverse-proxy mode. When enabled, TLS is terminated upstream and `X-Forwarded-*` headers are honored
**only** from the listed trusted IPs/CIDRs. See [Security → Reverse proxy](security#reverse-proxy).

```yaml
proxy:
  enabled: true
  trusted: ["127.0.0.1", "::1"]   # literal IPs or CIDRs; hostnames and "*" rejected
```

### `tls`

Direct HTTPS (TLS 1.2/1.3 + HTTP/2). Passwords come from env vars (see [Secrets](#secrets)). See
[Security → TLS & HSTS](security#tls--hsts).

When `proxy.enabled: true` the TLS **connector** is not created and the HTTPS-redirect plugin is
skipped, but the block is not fully ignored: `tls.hsts` still emits `Strict-Transport-Security`, and
`OMNISIGN_TLS_KEYSTORE_PASSWORD` is still **required** at startup merely because `tls:` is present. In
proxy mode, remove the `tls:` block rather than leaving it in place.

```yaml
tls:
  port: 18443
  keystorePath: "/path/to/keystore.p12"
  keyAlias: "omnisign"
  hsts:
    maxAgeSeconds: 31536000
    includeSubDomains: true
    preload: false
```

### `cors`

**Required.** `allowedOrigins` must be a non-empty list or `["*"]` — a missing block and an empty
list are both rejected so "didn't configure", "allow all", and "deny all" can't collapse into one
silent state. Entries may be bare host, `host:port`, or a full URL. See
[Security → CORS](security#cors).

```yaml
cors:
  allowedOrigins:
    - "https://sign.example.com"
  allowCredentials: false
```

`allowCredentials` (default `false`) lets a browser front-end on a different origin send its refresh
cookie and read the response. It is **rejected at startup** when combined with
`allowedOrigins: ["*"]` — with credentials enabled, the response reflects the caller's own `Origin`
back instead of emitting a literal `*`.

### `rateLimiting`

Per-IP token-bucket limits for `/auth/*` and the API routes. Omit to disable. See
[Security → Rate limiting](security#rate-limiting).

```yaml
rateLimiting:
  auth: { limit: 20, refillPeriodSeconds: 60 }
  api:  { limit: 200, refillPeriodSeconds: 60 }
```

### `auth`

SSO authentication (OIDC providers) and JWT sessions. Covered in full
on the [Authentication](authentication) page.

### `signingConfigFile`

Path to the [`signing.yml`](signing-policy) policy file (YAML, or `.json`). When omitted, the server
runs with built-in signing defaults and no profiles.

```yaml
signingConfigFile: "/etc/omnisign/signing.yml"
```

### `trustStoreDir`

Filesystem path to the server's writable trust directory, reconciled at boot from the
`trustedCertificates` declared in `signing.yml`. Defaults to a `trusted-certs` directory in the
server's **working directory** — in the Docker image that resolves to `/app/trusted-certs`, a mounted
volume, so leave it unset there. Set it only to relocate the store onto a specific mount.
Use a volume separate from the read-only policy and certificate files.

### `aia`

Where the server may download a missing issuer certificate from. When a certificate's issuer is
neither in the document nor among the trusted certificates, the server downloads it from the URL in
the certificate's Authority Information Access (AIA) extension. That URL comes from whoever made the
document, so by default the server refuses to download from loopback, private-network, link-local and
other non-public addresses. See [Security → Issuer downloads](security#aia).

```yaml
aia:
  allowPrivateAddresses: false   # true only if an internal CA publishes its issuers on an internal address
```

### `maxFileSize`

Maximum upload size in bytes. Defaults to `104857600` (100 MB).

### `organizationName`

Optional deploy-time branding label for the operator running this server (e.g.
`"University of Ostrava"`). It is surfaced in the [`GET /api/v1/health`](/server/api/get-health) and
[`GET /api/v1/capabilities`](/server/api/get-capabilities) responses as `organizationName`, alongside a fixed
`poweredBy: "OmniSign"`. Web and desktop clients compose it into the window title and toolbar (e.g.
`University of Ostrava · OmniSign`). When omitted or blank, no operator label is published and clients
show plain **OmniSign** — the product name is never replaceable, only prefixed.

```yaml
organizationName: "University of Ostrava"
```

## Minimal example

```yaml
listen:
  host: "127.0.0.1"
  port: 18080
operations:
  allowed: [VALIDATE]
cors:
  allowedOrigins: ["http://localhost:8080"]
```

See [`server.example.yml`](https://github.com/pizavo/omnisign/blob/main/server/src/main/resources/server.example.yml)
for the fully-commented template covering every block.
