# Signing policy (`signing.yml`)

`signing.yml` is the **provider-authored signing and validation policy** — the server's equivalent of
the desktop "global settings + profiles". It holds *how* the server signs and validates: default
algorithms, signature level, OCSP/CRL timeouts, the TSA, the validation policy, trusted certificates,
and named profiles. It is loaded **read-only** at startup; point [`server.yml`](configuration)'s
`signingConfigFile` at it.

A fully-commented template ships as **`signing.example.yml`** (in `server/src/main/resources/`).

- **YAML** is the primary format; a path ending in `.json` is parsed as JSON.
- **`${VAR}` substitution** — any value may reference an environment variable, expanded at load, so
  secrets live in the environment, not the file (the TSA password works this way). A referenced-but-
  unset variable fails startup. A name that starts with `OMNISIGN_` can also be set in a file, such
  as the one `OMNISIGN_TSA_PASSWORD_FILE` names (see
  [Secrets in files](configuration#secrets-in-files)).
- **Unknown keys fail startup.** The desktop-only `AppConfig` fields (`activeProfile`, `tlDrafts`,
  `renewalJobs`, `schedulerConfig`) are not part of this schema and are rejected if present.
- **Values must say what they mean**, under the [same rules as `server.yml`](configuration#resolution-order):
  a boolean key takes only `true` or `false`, a null for a number or boolean fails startup, and so does
  a second document in the file.

## `global`

Defaults applied to every operation unless a profile or a strictly-tightening per-request override
narrows them.

```yaml
global:
  defaultHashAlgorithm: SHA256          # SHA256|SHA384|SHA512|SHA3_256|SHA3_384|SHA3_512|WHIRLPOOL|RIPEMD160
  # defaultEncryptionAlgorithm: RSA_SSA_PSS   # omit to infer from the certificate key
  defaultSignatureLevel: PADES_BASELINE_B     # B | LT | LTA (T is a runtime-only fallback, rejected here)
  disabledHashAlgorithms: [RIPEMD160, WHIRLPOOL]
  # disabledEncryptionAlgorithms: [DSA]
  ocsp: { timeout: 30000 }
  crl:  { timeout: 30000 }

  # RFC 3161 TSA — required for T / LT / LTA. Password from the environment only.
  # timestampServer:
  #   url: "http://tsa.example.org/tsr"
  #   username: "omnisign"
  #   password: "${OMNISIGN_TSA_PASSWORD}"
  #   timeout: 30000

  validation:
    policyType: DEFAULT_ETSI            # or CUSTOM_FILE (+ customPolicyPath)
    checkRevocation: true               # also refuses SIGNING with a revoked certificate
    useEuLotl: true
    # alertIfNotEuLotl: false           # flag signatures whose anchor is not on the EU LOTL
    # allowExpiredCertificate: false    # allow SIGNING with an expired certificate
    #                                   # (signing only; such signatures fail validation)
    # customTrustedLists:               # extra ETSI TS 119612 lists, by reference
    #   - name: "national-tl"
    #     source: "https://tl.example.gov/tl.xml"     # https:// or file://
    #     signingCertPath: "/etc/omnisign/tl-signing.crt"  # used only while its signature verifies
    # trustedCertificates:              # directly-trusted anchors, by reference
    #   - path: certs/internal-root.pem # exactly one of path | inline
    #     type: ANY                     # ANY | CA | TSA
    #     fingerprint: "sha256-<hex>"   # optional integrity pin (fails startup on mismatch)
    # algorithmConstraints:
    #   expirationLevel: FAIL           # FAIL | WARN | INFORM | IGNORE
    #   expirationLevelAfterUpdate: WARN
    #   policyUpdateDate: "2026-02-01"
    #   expirationDateOverrides: { SHA512: "2035-01-01", "RSA:1900": "2030-12-31" }

  # customPkcs11Libraries:              # only when the server signs with a PKCS#11 token
  #   - { name: "vendor-token", path: "/usr/lib/vendor-pkcs11.so" }
  pkcs11ProbeTimeoutSeconds: 30
  trustedListRefreshIntervalHours: 4
```

Keep `trustedListRefreshIntervalHours` at or below **6**. The ETSI validation policy treats a
trusted list as fresh only for 6 hours after its last successful synchronization, so a longer
interval leaves every qualified validation reporting *"the trusted list is not considered as
fresh"* for the rest of each cycle. Re-synchronizing an unchanged list is cheap — it is
re-stamped on a matching digest, without being re-parsed or re-verified. A list that cannot be
downloaded is still served from the copy in the server's trusted-list cache, however old, and
validation reports name it as not refreshed. The server then tries to download it again every
5 minutes, up to 6 times, before going back to the interval. The freshness check counts from when
a list was last loaded, so it does not flag such a copy; the report's notice does.

With `policyType: CUSTOM_FILE`, the server validates under the DSS validation policy file that
`customPolicyPath` names, never under the default ETSI policy. While the path is unset, or the file
is missing, unreadable or not a validation policy, every validation request fails with
`500 INVALID_POLICY`. The response does not name the file. The server's log does, at ERROR level,
with the reason the file cannot be used.

A key in `algorithmConstraints.expirationDateOverrides` is an algorithm name, or `NAME:KEY_SIZE`
for one key-size entry of an algorithm the validation policy dates by key size, such as
`"RSA:1900"` (quoted, because of the colon). A bare name of such an algorithm only moves its
dates earlier, so it never makes a weak key acceptable again. The CLI's
[expiration date overrides](/cli/configuration/overview#expiration-date-overrides) section explains
how the entries combine.

A `defaultEncryptionAlgorithm`, or a profile's `encryptionAlgorithm`, has to suit the signing key:
`RSA_SSA_PSS` can take the place of `RSA` on an RSA key, and `PLAIN_ECDSA` that of `ECDSA` on an EC
key, but a sign request with one of another family is refused, and so is one with `RSA_SSA_PSS` or
`PLAIN_ECDSA` and a key on a PKCS#11 token, which cannot sign with them; sign from a PKCS#12 file,
with [`signingKeystorePath`](configuration#operations), to use them. Left unset, the key's own
algorithm signs. The CLI's [algorithms](/cli/commands/algorithms) page says more.

**`PADES_BASELINE_T` cannot be configured** — neither as `global.defaultSignatureLevel` nor as a
profile's `signatureLevel`. The server rejects it at startup and points you to `PADES_BASELINE_LT`.
B-T is only ever a *runtime fallback*, applied automatically when a B-LT sign cannot obtain revocation
data; configuring it as a target would silently produce B-B.

### Trusted certificates

`trustedCertificates` are declared **by reference** and reconciled into the server's writable
[`trustStoreDir`](configuration#truststoredir) at boot. Each entry sets exactly one of `path` (a
PEM/DER file, relative to `signing.yml`) or `inline` (Base64 DER, in which line breaks and spaces
are ignored, so a wrapped PEM body pasted as a YAML block works), plus a required `type`
(`ANY`/`CA`/`TSA`) and an optional `fingerprint` integrity pin, checked before the certificate is
stored. The bytes are copied into the trust directory, so the source file may be removed afterward.
A fatal reconcile condition (integrity mismatch, unresolvable reference, a trust directory whose
index cannot be read) aborts startup.

A signature counts as trusted only when its trust anchor has the type `CA` or `ANY`, a timestamp
only when its anchor has `TSA` or `ANY`. The anchor is the first trusted certificate in the chain,
counting from the signer, because validation stops there: when an issuing CA is trusted, the type
of the root above it does not count. A certificate a trusted list also trusts keeps that trust,
whatever its type.

A profile may also declare its own `validation.trustedCertificates`; each profile gets its own trust
scope, and a profile removed from the policy has its scope cleared at the next boot.

## `profiles`

Named overrides selected per request via the `profile` **multipart form field** — a `profile=archival`
part sent alongside `file`. There is no query-string form. A profile's identity is its inner `name`; a
name appearing in more than one source fails startup. Every per-profile field is optional and
overrides the matching `global` value. That holds inside `validation` too: a profile that sets only some
of its keys, such as `trustedCertificates`, keeps the global `policyType`, `checkRevocation` and
`useEuLotl`.

Profiles come from any combination of three sources:

```yaml
profiles:
  inline:                              # 1. defined directly
    - name: archival
      description: "Long-term archival (B-LTA)"
      hashAlgorithm: SHA512
      signatureLevel: PADES_BASELINE_LTA
  # files:                             # 2. one bare profile per file
  #   - profiles/archival-lta.yml
  # directories:                       # 3. scanned recursively for *.yml / *.yaml
  #   - profiles/
```

See [`signing.example.yml`](https://github.com/pizavo/omnisign/blob/main/server/src/main/resources/signing.example.yml)
for the fully-commented template, and the [API reference](/server/api/omnisign-server-api) for how clients select a
profile per request.
