# Security

The server defaults are deliberately closed: it binds to **loopback**, allows only **`VALIDATE`**,
and refuses to expose itself insecurely. This page covers the transport, network, and operation-level
controls; the [Configuration](configuration) page has the exact field syntax for each block.

## Transport security

`listen.host` defaults to `127.0.0.1`, reachable only from the same machine. The moment you bind to a
**non-loopback** host (`0.0.0.0` or a specific IP), the server **requires** either a [`tls:`](#tls--hsts)
block or [`proxy.enabled: true`](#reverse-proxy). Otherwise startup is refused: plain HTTP
on a network-reachable interface would expose JWT bearer tokens, OIDC callback parameters, and refresh
tokens to any on-path observer.

`development: true` is likewise refused on a non-loopback host: dev mode echoes internal exception
details to clients. Keep it `false` everywhere except local debugging on `127.0.0.1`.

## TLS & HSTS

A `tls:` block enables direct HTTPS with **TLS 1.2/1.3 and HTTP/2** (ALPN). To force TLS 1.3 only,
launch with `-Djdk.tls.disabledAlgorithms=TLSv1,TLSv1.1,TLSv1.2`. Keystore and private-key passwords
come from the environment, never from YAML (see [Secrets](configuration#secrets)); a `.p12`/`.pfx`
path is read as PKCS#12, anything else as JKS.

Enable **HSTS** (`tls.hsts`) only when *all* traffic is HTTPS — sending it over plain HTTP can lock
users out. Start with a short `maxAgeSeconds` (e.g., 300) and raise to a year once stable. Behind a
TLS-terminating proxy, let the proxy inject HSTS instead.

## CORS

`cors.allowedOrigins` is **required** — a list of explicit origins or `["*"]`. A missing block and an
empty list are both rejected at startup, so "didn't configure CORS", "allow all", and "deny all" can
never collapse into the same silent state. Entries may be a bare host, `host:port`, or a full URL.
Set this to your web frontend's origin(s) before deployment.

## Rate limiting

`rateLimiting` applies per-IP token buckets to the `/auth/*` routes (`auth`) and the operational API
(`api`); system routes are never limited. Defaults are 20 requests / 60 s for `auth` and 200 / 60 s
for `api`; over-quota requests get `429 Too Many Requests` with `Retry-After`. Omit the block to
disable. Behind a proxy, client IPs are taken from `X-Forwarded-For` only for connections from a
[trusted proxy](#reverse-proxy).

## Reverse proxy

With `proxy.enabled: true`, TLS is terminated upstream (nginx, Caddy, Traefik) and the server runs on
the plain-HTTP connector. Only `X-Forwarded-For` is honored — its **first** entry becomes the client
IP — and only when the TCP source IP matches an entry in `proxy.trusted` (literal IPs or CIDRs;
hostnames and `*` are rejected), so a client reaching the Ktor port directly cannot spoof its IP.
`X-Forwarded-Proto` and `X-Forwarded-Host` are deliberately **not** consumed; use
`OMNISIGN_EXTERNAL_URL` to tell the server its public scheme and host. `proxy.enabled: true` requires
a non-empty `trusted` list. See [Deployment → Reverse proxy](deployment#reverse-proxy).

## Operation gating {/* #operation-gating */}

`operations.allowed` controls which operations the API exposes. It defaults to **`VALIDATE`** only —
the one operation that exposes no signing material or timestamping endpoint. **`SIGN`** and
**`TIMESTAMP`** are opt-in:

```yaml
operations:
  allowed: [VALIDATE, SIGN]
  certificateAliases: ["University Seal-1f3a@pkcs11-5A3C0F12"]   # optional allowlist; only meaningful with SIGN
```

- **`SIGN`** exposes the server's signing certificates (and gates `GET /api/v1/certificates`). When
  enabled, the server logs a warning unless authentication is on, because every network-reachable
  client could otherwise sign. Restrict the usable certificates with `certificateAliases` for
  defense-in-depth, listing the aliases exactly as `GET /api/v1/certificates` returns them. The
  server then signs only with a listed certificate: a request without a
  `certificateAlias` uses the only listed alias, and when the list holds several, the request has
  to name one.
- **`TIMESTAMP`** exposes the server's pre-configured TSA via `POST /api/v1/timestamp` and
  `POST /api/v1/timestamp/inspect`.

Combine the allowlist with [authentication](authentication) for any internet-facing `SIGN` deployment.

## Issuer downloads (AIA) {/* #aia */}

When a certificate's issuer is neither in the document nor among the trusted certificates, the server
downloads it from the URL in the certificate's Authority Information Access (AIA) extension. It does
so while it builds the chain, before it knows whether the chain is trusted, so the URL is whatever the
maker of the document put there, and `VALIDATE` is enabled by default. Every such download:

- uses only `http` or `https`; `file`, `ftp` and `ldap` URLs are skipped;
- must finish within the shorter of the OCSP and CRL timeouts in `signing.yml` (30 seconds each by
  default), so a server that answers a byte at a time is cut off;
- reads at most 1 MiB of response.

The server also refuses to connect to loopback, private-network (RFC 1918 and IPv6 unique-local),
carrier-grade NAT, link-local and other non-public addresses, which include the cloud metadata
endpoint `169.254.169.254` and Azure's host endpoint `168.63.129.16`. An IPv6 address that carries an
IPv4 one, such as `::ffff:10.0.0.1` or the 6to4 address `2002:a00:1::`, is judged by the IPv4
address. The check applies to the address the server actually connects to, so it also covers
redirects and host names that resolve to an internal address. If an internal CA publishes
its issuer certificates on an internal address and your documents don't embed them, allow internal
addresses in `server.yml`:

```yaml
aia:
  allowPrivateAddresses: true
```

The server logs a warning at startup while this is on. Revocation data (CRL and OCSP) is fetched only
for chains that end at a trusted certificate, so its URLs come from trusted CAs and are not
restricted this way. The desktop app and the CLI apply the same scheme, time and size limits but allow
internal addresses, because they process their own user's documents.

## Other hardening

- **Strict config parsing** — unknown `server.yml` keys fail startup so a typo can't silently disable
  a defense (see [Configuration](configuration)).
- **Secrets never in YAML** — the JWT secret, OIDC client secrets, and the TLS, TSA, and file
  signing-keystore passwords come from environment variables, from files those variables name, or
  from systemd credentials. A secret file is read only if its owner and mode keep it private (see
  [Secrets in files](configuration#secrets-in-files)).
- **No keychain without `SIGN`** — a server that only validates or timestamps never opens the
  operating system's keychain. A signing server does, because the server cannot prompt and that is
  where it looks up the PIN of a PIN-protected PKCS#11 token: service `omnisign-token`, with the
  token's id as the account (`omnisign diagnose pkcs11` lists the ids). If the token refuses that
  PIN, the server logs a warning and doesn't send the same PIN to that slot again until the entry
  changes or the server restarts, so a stale entry can't use up the token's PIN retries.
- A request body may be at most `maxFileSize` plus 1 MiB for the form fields, whether it declares
  its length or arrives chunked. The upload endpoints answer a larger one with `413`; the session
  endpoints, which take a small JSON body or none, treat it as missing. A multipart request may
  carry at most 32 parts, and only one of them a file. The file is streamed to disk and bounded by
  `maxFileSize`.
- Validation, signing and timestamping run off the threads that answer requests, on at most as
  many documents at once as the server has processors. A document whose revocation or timestamp
  servers answer slowly can delay only the documents queued behind it, not the health check,
  sign-in or other requests.
- Every response carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: strict-origin-when-cross-origin`, and
  `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`. No `X-Powered-By` is sent.
- A client-supplied `X-Request-Id` is accepted only if it matches `[a-z0-9+/=-]` and is 1–64
  characters; anything else is replaced by a server-generated UUIDv7. The character check is what
  stops CRLF injection into the MDC log context.
