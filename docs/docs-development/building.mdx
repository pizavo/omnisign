# Building and running


import OsTabs from '@site/src/components/OsTabs';
import TabItem from '@theme/TabItem';

Every command below is a Gradle task run through the wrapper. Use `./gradlew` on Linux and macOS, and
`gradlew.bat` on Windows. The examples show the Windows form where the two differ.

`--enable-native-access=ALL-UNNAMED` is already configured in `gradle.properties` and in each module's
build script, so you never need to pass it yourself. The build also has the Gradle configuration cache
and build cache enabled.

## Running each target

### Desktop

<OsTabs>
    <TabItem value="windows" label="Windows">

        ```powershell
        .\gradlew.bat :composeApp:run
        ```

    </TabItem>
    <TabItem value="linux" label="Linux">

        ```bash
        ./gradlew :composeApp:run
        ```

    </TabItem>
    <TabItem value="macos" label="macOS">

        ```bash
        ./gradlew :composeApp:run
        ```

    </TabItem>
</OsTabs>

Requires **JBR 25** — see [the prerequisites](index.mdx#prerequisites). This is the only target with a
vendor-specific toolchain.

### Server

```bash
./gradlew :server:run
```

Listens on `http://localhost:18080` unless a `server.yml` says otherwise. `:server:run` additionally
passes `--config server/src/main/resources/server.yml` when that file exists — it is gitignored, so a
fresh clone starts on the built-in defaults; copy `server.example.yml` next to it to customise a
development run. Configuration resolution is described in
[Server → Configuration](/server/configuration).

### CLI

```bash
./gradlew :cli:run --args="--help"
```

Pass CLI arguments through `--args`. Note that interactive prompts (PIN entry) work under `:cli:run`
because the build forwards the parent terminal's stdin.

### Web

```bash
./gradlew :composeApp:wasmJsBrowserDevelopmentRun
```

Starts a development server and opens the app in your default browser. The browser client needs a
running [OmniSign Server](/server/) to do anything useful — on its own it can open and view a PDF, but
signing and validation are HTTP calls.

Which server it calls is baked in at **build time**: `generateBuildConfig` reads the
`OMNISIGN_SERVER_URL` environment variable into `BuildConfig.SERVER_URL`. Leaving it unset means
*same origin*, which is correct when one OmniSign Server hosts both the bundle and the `/api/v1`
routes. For a separate development server, set it explicitly:

```bash
OMNISIGN_SERVER_URL=http://localhost:18080 ./gradlew :composeApp:wasmJsBrowserDevelopmentRun
```

```powershell
$env:OMNISIGN_SERVER_URL='http://localhost:18080'; .\gradlew.bat :composeApp:wasmJsBrowserDevelopmentRun
```

An already-built bundle can be retargeted without recompiling by serving a `web-config.json` next to
`index.html` — it is read at startup and takes precedence over `BuildConfig.SERVER_URL`.

:::warning[A cold Wasm build can produce a broken bundle]
Immediately after `:composeApp:clean`, the first *development* Wasm build sometimes emits a mismatched
JavaScript-glue and `.wasm` pair. The app then fails at load with:

```text
LinkError: WebAssembly.instantiate(): Import #0 "./skiko.mjs" "externrefToBoolean": function import requires a callable
```

Running the production task once regenerates a consistent pair and unblocks the development task:

```bash
./gradlew :composeApp:wasmJsBrowserProductionRun
```
:::

## Producing artifacts

| Target | Task | Output |
| --- | --- | --- |
| CLI fat JAR | `:cli:shadowJar` | `cli/build/libs/omnisign-*.jar` |
| CLI installer | `:cli:jpackage` | Windows: MSI + app-image; Linux: DEB + RPM + app-image; macOS: DMG + PKG — all under `cli/build/jpackage/` |
| Desktop installer | `:composeApp:packageDistributionForCurrentOS` | MSI + EXE (Windows), DMG + PKG (macOS), DEB + RPM (Linux), plus the jpackage app-image directory on every OS |
| Desktop Linux packages | `:composeApp:packageDeb`, `:composeApp:packageRpm` | `composeApp/build/compose/binaries/main/deb/` and `.../rpm/` |
| Server fat JAR | `:server:buildFatJar` | `server/build/libs/server-all.jar` |
| Server dist | `:server:installDist` | `server/build/install/server/bin/server` |
| Web bundle | `:composeApp:wasmJsBrowserDistribution` | `composeApp/build/dist/wasmJs/productionExecutable/` |
| API docs | `:dokkaGenerate` | `build/dokka/html/` |

Both packaging tasks also expose one task per format, which is what the release workflows invoke so
each runner produces only what it can: `:composeApp:packageMsi`, `:composeApp:packageDmg`, and
their `:cli:jpackage*` counterparts.

The desktop DEB and RPM are the exception. `:composeApp:packageDeb` and `:composeApp:packageRpm`
keep the names the plugin would have used, but the build declares them itself and they call
jpackage directly on the app-image that `:composeApp:createDistributable` produces. The plugin appends
its own `--resource-dir` after any argument the build adds, and jpackage keeps only the last
occurrence of a repeated option, so the desktop-entry and packaging-script overrides in
`composeApp/packaging/linux/` can only be applied by invoking jpackage ourselves. Those overrides
are what give the launcher its `%f` field code (without which the shell cannot hand a PDF to the
app), its `StartupWMClass`, and the AppStream metainfo and hicolor icon the maintainer scripts
install. The field code is `%f` rather than `%U` because GIO expands `%U` to `file://` URIs, and
the app accepts only a path.

jpackage builds the Linux packages on an Ubuntu runner, and that leaves gaps that the build closes
around each jpackage run:

- **DEB dependencies.** jpackage names each dependency after the package that owns the library on the
  build host. The release runners are past Debian's 64-bit `time_t` transition, so some of those
  names carry its `t64` suffix (`libasound2t64`), which Ubuntu 22.04 and Debian 12 never had. Both
  modules rewrite the DEB's `Depends` field so that each such entry becomes an alternative with its
  old name (`libasound2t64 | libasound2`), and one DEB installs on both generations.
- **RPM dependencies.** jpackage looks up which package provides each library only for the host's
  own package format, so on Ubuntu it skips the lookup for the RPM, and the RPMs required nothing but
  `xdg-utils`. The build instead reads the `DT_NEEDED` entries of every ELF object in the app-image,
  drops the libraries the image bundles, and passes the rest to `--linux-package-deps` as soname
  capabilities such as `libasound.so.2()(64bit)`. Every RPM distribution provides those under the
  same name, whereas package names differ (`alsa-lib` on Fedora, `libasound2` on openSUSE). The CLI
  reads them from the image `:cli:jpackageLinuxImage` builds, which holds the same native code as
  its RPM. Libraries loaded with `dlopen`, such as the PC/SC library smart-card access uses, leave no
  such entry and are not declared.
- **RPM directory ownership.** The spec templates work out which directories the package owns by
  subtracting the `filesystem` package's, falling back to a built-in list where
  `rpm -ql filesystem` fails, as it does on Ubuntu. jpackage's own template prints that list on a
  single line, so nothing was subtracted, and the RPMs claimed `/opt`, `/usr`, `/usr/share` and
  `/usr/share/licenses` as their own. The templates print one directory per line instead. This
  matters once a package ships a file in `/usr/bin`: Fedora's `filesystem` gives that directory
  mode 0555, and a package claiming it with another mode is refused as a file conflict.
- **The CLI's command.** Both CLI packages ship `/usr/bin/omnisign`, a symlink to the launcher in
  `/opt/omnisign-cli`, as a file of the package: the DEB gets it when it is rebuilt with `dpkg-deb`,
  and the RPM spec creates it in `%install`. Up to 1.21.1 the maintainer scripts created
  `/usr/local/bin/omnisign` instead, which Debian Policy §9.1.2 forbids, since `/usr/local` belongs
  to the administrator. On upgrade, the old DEB's `prerm` removes that link, and the new RPM's `%post`
  removes it if it still points at the CLI.

The CLI's installers create no shortcuts and no menu or desktop entries. Its launcher is a console
program, so a shortcut would open it in a console window that closes again as soon as it exits. The
MSI puts the command on `PATH` instead, and the Linux packages ship `/usr/bin/omnisign`. The Linux
packages are also built without `--icon`, because jpackage turns a custom icon into a desktop entry.
The entry brings an `xdg-utils` dependency and install scripts that register it with
`xdg-desktop-menu`, a command that fails on hosts with no applications directory, such as servers
and containers. Up to 1.21.1 both Linux packages carried such an entry, hidden from menus. The DEB
never registered it, and the old RPM's `%preun` unregisters it during the upgrade, just as an MSI
upgrade removes the shortcuts older versions created.

Native installers are built by [`jpackage`](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html)
and can only target the OS they run on — there is no cross-packaging. Producing all of them means
building on all three platforms, which is what the release workflows do.

Note that Compose's `TargetFormat.AppImage` is jpackage's `--type app-image`: a self-contained
*directory* under `composeApp/build/compose/binaries/main/app/`, not a Linux `.AppImage` bundle. It is
declared for the current OS, so `packageDistributionForCurrentOS` produces it on every platform
alongside the installers. `:composeApp:createDistributable` builds the same directory on its own,
which is what the Windows and macOS release jobs use.

Deployment guidance for the two server-side artifacts lives with its audience:
[Server → Deployment](/server/deployment) and [Web → Deployment](/web/deployment).

## The Wasm npm lockfile

The web target has npm dependencies — currently just `mupdf` — and their lockfile is committed under
`kotlin-js-store/wasm/`.

:::warning[A clean compile does not mean the lockfile is current]
`compileKotlinWasmJs` succeeds against a stale lock. Nothing tells you it drifted until CI runs
`kotlinWasmStorePackageLock` and fails.

After adding, removing, or updating **any** npm dependency — including a version-catalog edit that an
`npm(...)` declaration consumes — regenerate it and commit the result:

```bash
./gradlew kotlinWasmUpgradePackageLock
```

This is a **root-project** task — qualifying it as `:composeApp:kotlinWasmUpgradePackageLock` fails
with `Task 'kotlinWasmUpgradePackageLock' not found in project ':composeApp'`.

The one time you must *not* run it is when `storePackageLock` fails only on a release build. That is a
different problem, explained in [Releases and CI](releases.mdx#building-the-artifacts).
:::

## Other useful tasks

```bash
./gradlew build                        # compile everything and run all tests
./gradlew :shared:updateLotlKeystore   # refresh the bundled EU LOTL keystore
./gradlew :shared:regenerateDssMessages -Plocale=cs -Padditions=new-cs.properties
                                       # rebuild a DSS message translation after a DSS upgrade
./gradlew regenerateTestPki            # regenerate the end-to-end test PKI key stores
./gradlew generateIcons                # regenerate .ico/.icns/PNG icons from the masters
```

`build` includes the two `wasmJsBrowserTest` tasks, which run under karma in a headless Chrome — so a
full build needs a browser available, unlike every other test task. Run the JVM suites individually
if you do not have one; see [Testing](testing.mdx#the-browser-suites).

`updateLotlKeystore` downloads the current Official Journal keystore from the DSS demonstrations
repository into `shared/src/jvmMain/resources/lotl-keystore.p12`. Run it when the European Commission
rotates the LOTL signing keys, and commit the result.

`regenerateDssMessages` rebuilds the Czech or Slovak DSS message bundle against the DSS version on
the classpath, merging the translations in the additions file; see
[The DSS validation report](i18n.mdx#the-dss-validation-report) for when and how.

`regenerateTestPki` replaces the CA, signer and TSA key stores the end-to-end tests sign with, in
`shared/src/jvmTest/resources/e2e/` and, for the signer and the TSA, `cli/src/test/resources/e2e/`.
Every key is RSA-4096 because a smaller one would age out of DSS's validation policy long before the
certificates do: DSS 6.5.1 accepts 2048-bit RSA only until 1 January 2027, after which every test
signing with such a fixture would fail on the fixture rather than on the code. The certificates
themselves last until the 2120s, so run it only when the algorithm policy moves again, and commit the
five key stores. It uses the `keytool` of the JDK running Gradle.

`generateIcons` needs ImageMagick 7 (`magick`) and `icnsify` on the `PATH`. It rewrites the icons in
`assets/icons/` and copies them into the places that consume them, including this documentation site's
favicon and logo.

:::note[The API reference does not cover the browser target]
`:dokkaGenerate` suppresses the Wasm source sets in **both** `shared` and `composeApp` (`composeApp`
also suppresses any source set named `web*`), because Dokka cannot fully process Wasm targets. The
`webMain` `actual` implementations and `shared`'s `Remote*` classes are therefore absent from the
[API reference](https://pizavo.github.io/omnisign/api/); read them in the source tree instead.
:::
