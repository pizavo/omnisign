# Working with DSS

Every signature OmniSign creates or checks is ultimately produced by
**[DSS](https://github.com/esig/dss)** — *Digital Signature Services*, the European Commission's
reference implementation of the eIDAS signature standards. OmniSign uses **DSS 6.3**.

DSS is a large, stateful Java library with an API shaped by the ETSI specifications rather than by
ergonomics. Most of the code in `shared/src/jvmMain/data/repository/` exists to keep that shape from
leaking into the rest of the application.

## Signing, end to end

Where the repository does the work, and where DSS does. Note that the signing identity resolves from
**either** a PKCS#11 token **or** a PKCS#12 keystore file, and that the optional blocks are keyed to
the requested PAdES level — a B-B signature never contacts a TSA.

## The factory that owns the expensive things

`DssServiceFactory` centralises everything costly or shared: TSP sources, certificate verifiers, and —
via the `TrustedSourceRegistry` it delegates to — one retained `TLValidationJob` per distinct trust
source. It is a Koin `single`, injected into all three DSS repositories (`DssSigningRepository`,
`DssValidationRepository`, `DssArchivingRepository`) and into `TrustedListRefreshScheduler`.

It builds a **different certificate verifier for each of the three operations**, and the difference is
not cosmetic — they barely overlap:

| Alert | Signing | Extension | Validation |
| --- | --- | --- | --- |
| `alertOnUncoveredPOE` | raised | raised | raised |
| `alertOnNoRevocationAfterBestSignatureTime` | suppressed | **raised** | raised |
| `alertOnMissingRevocationData` | suppressed | **raised** | suppressed |
| `alertOnInvalidTimestamp` | raised | raised | suppressed |
| `alertOnRevokedCertificate` | raised | raised | suppressed |
| `alertOnExpiredCertificate` | DSS default (aborts) | DSS default (aborts) | suppressed |
| `alertOnNotYetValidCertificate` | DSS default (aborts) | DSS default (aborts) | suppressed |

Signing and extension share a body (`buildSigningCertificateVerifier` and
`buildExtendCertificateVerifier` both delegate to one private builder); both set
`isCheckRevocationForUntrustedChains = false` and honour `validation.allowExpiredCertificate` by
clearing `alertOnExpiredCertificate`.

Signing suppresses the two revocation alerts because they fire in the verifier's pre-extension check,
before the PAdES extension embeds CRL/OCSP data — on a signing operation that reaches B-LT or B-LTA
they describe a gap the very next step closes.

**Extension keeps them**, because there is no next step: embedding that data *is* the operation. It
can fail in two shapes, and only one of them is visible in the resulting level:

- the revocation data cannot be fetched — the DSS dictionary holds certificates and nothing else, and
the document stays at B-T;
- it *is* fetched and embedded but cannot be used, because it postdates the signing certificate's
expiry. DSS's baseline-LT check counts the embedded CRL, so the level reads **B-LT** even though
`RevocationDataVerifier` discards that CRL at validation time.

The second shape is why these alerts carry their weight: the level cannot tell it from a genuine
promotion, and only the captured warnings can. Note also that suppressing
`alertOnMissingRevocationData` removes the abort it would otherwise cause: DSS skips the check
entirely when the alert is null rather than falling back to throwing, so nothing else stops an
augmentation that embedded nothing. `DssArchivingRepository` turns the captured warnings into
`ArchivingResult.revocationDataMissing` (only for targets ≥ B-LT, since B-T needs no revocation
data); the desktop asks before saving such a document, the CLI refuses to write it, and the renewal
scheduler leaves the original file untouched.

`ArchivingResult.newSignatureLevel` is the level the output **actually reached**, not the one that
was requested: `DssArchivingRepository` reads it back out of the produced bytes with DSS's own
`getDataFoundUpToLevel`, the same determination that drives the level in a validation report, so the
two can never disagree. It matters here because DSS's LT requirement is non-empty CRL/OCSP data for
the chain — not the presence of a DSS dictionary — so a dictionary holding only certificates reports
B-T. The typed `achievedLevel` carries the same answer for callers that compare it against what they
asked for; the renewal scheduler does exactly that before overwriting anything, and treats a level it
could not establish as a failure rather than a pass — an archival job may only replace a file it has
confirmed is stronger.

The same helper fills `DocumentTimestampInfo.level`, which is what the desktop extension dialog
displays, and `containsLtData` is derived from that level. The presence of a `/DSS` dictionary is
never consulted — it can be there and hold nothing usable, which is exactly how a B-T document comes
to be labelled B-LT by tools that read structure instead of content. `hasDocumentTimestamp` remains
a structural fact used to decide which extension options apply, not to infer a level: a document
timestamp over missing or unusable validation data is still a B-T document.

Validation suppresses almost everything for the opposite reason: it opens with
`silenceAlertsCoveredByTheReport()`, which clears every alert whose condition the ETSI report already
states as an indication, so the alerter adds no duplicates. For `alertOnExpiredCertificate` and
`alertOnNotYetValidCertificate` there is a harder reason: DSS defaults both to `ExceptionOnStatusAlert`,
so leaving them active would turn a readable INDETERMINATE / `OUT_OF_BOUNDS_NO_POE` report into a
failed *operation* with no report at all. Collapsing the two verifiers into one is the obvious-looking
refactor, and it is wrong.

Both paths short-circuit when `config` is `null` or `validation.checkRevocation` is off. Validation
returns a fully lenient verifier, every alert cleared; signing clears the five revocation- and
timestamp-related alerts but leaves the expired- and not-yet-valid-certificate alerts at their DSS
defaults, so an expired signing certificate still aborts unless `validation.allowExpiredCertificate`
is set.

Three more builders round it out. `buildCertificateVerifier(timeout)` returns a lenient verifier with
AIA/OCSP/CRL sources but no config and no alerts. `buildTspSource()` constructs an `OnlineTSPSource`
per configured timestamp server, wiring in that server's timeout and credentials.
`buildPdfObjectFactory()` returns a `PdfBoxNativeObjectFactory` that spills large documents to a
temporary file once the in-heap limit is exceeded, so signing a large PDF does not scale with its size
in memory.

## How a DSS warning becomes a sentence

DSS reports problems in two incompatible ways: through *alerts* on the `CertificateVerifier`, and by
logging to SLF4J. OmniSign captures both, then normalises them.

1. **`CollectingStatusAlert`** is registered on the `CertificateVerifier`. Instead of throwing or
printing, it accumulates DSS's status messages for the duration of an operation.
2. **`DssLogCapture`** attaches a capturing Logback appender — by reflection, so `shared` needs no
compile-time `logback-classic` dependency — to the `eu.europa.esig` parent logger while an operation
runs. It catches the diagnostics DSS only ever logs, minus the `eu.europa.esig.dss.tsl.` loggers,
whose output the separate trusted-list warning mechanism handles. It is *not* `Closeable` — it is
started and stopped in a `try`/`finally`.
3. **`DssWarningSanitizer`** classifies each raw message into a `WarningCategory` and folds the
affected certificate identifiers together, so ten warnings about ten certificates become one
sentence.

The categories, and roughly what each means:

| Category | Meaning |
| --- | --- |
| `REVOCATION_NOT_FOUND` | CRL/OCSP could not be downloaded |
| `REVOCATION_AFTER_CERTIFICATE_EXPIRY` | Revocation data was retrieved but rejected: it was issued after the certificate expired, and the issuer asserts no knowledge of that period |
| `REVOCATION_UNTRUSTED_CHAIN` | Revocation was skipped — the chain has no trusted anchor |
| `REVOCATION_STATUS_UNKNOWN` | Neither *good* nor *revoked* could be established |
| `REVOCATION_POE_MISSING` | Revocation data needed for proof-of-existence is absent |
| `REVOCATION_POE_STALE` | Revocation data was collected, but every response predates the timestamp whose proof-of-existence it has to cover |
| `FRESH_REVOCATION_MISSING` | Revocation data for the signing chain predates the signature's own timestamp, so none of it covers the moment of signing |
| `TIMESTAMP_UNTRUSTED` | The issuing TSA is not in any trusted list |
| `CERTIFICATE_PARSE_ERROR` | Malformed ASN.1 extensions, typically in a third-party TSA certificate |
| `TSP_FAILURE` | The timestamp server returned a `PKIFailureInfo` |

Each category renders itself through `toSummary(ids, nextUpdate)`, which is where the user-facing
wording lives. `nextUpdate` is the time DSS reports newer revocation data as due; the two
stale-revocation categories use it to pick a `_BY_TIME` template over their `_GENERIC` one, and every
other category ignores it. The result is a list of `AnnotatedWarning`.

:::tip[Warnings are suppressed per operation, not globally]
`DssSigningRepository` deliberately suppresses `REVOCATION_NOT_FOUND`, `FRESH_REVOCATION_MISSING`, and
`CERTIFICATE_PARSE_ERROR`. Not because they are unimportant, but because at *signing* time they are
expected noise — the signature being created has no revocation data yet, and third-party TSA
certificates routinely carry extensions DSS cannot parse. The same categories are surfaced during
validation, where they mean something.

If you add a category, decide explicitly what each repository does with it — including whether it
belongs in `blocksLongTermMaterial`, the wider set that tells the archiving path an augmentation did
not reach its target level. `REVOCATION_POE_STALE` and `FRESH_REVOCATION_MISSING` are deliberately
outside it: that data *was* embedded, it just does not yet cover the time it has to.
:::

## Timestamp failures

`TspErrorDetector` pulls RFC 3161 `PKIFailureInfo` codes out of the exceptions DSS throws when a
timestamp authority rejects a request. Without it, a TSA saying *"policy not supported"* and a TSA
being unreachable are the same opaque failure.

A TSP failure can be non-fatal: DSS may retry and succeed, in which case the failure survives only as
a logged warning that `DssLogCapture` picks up. That is why `TSP_FAILURE` exists as a warning category
*and* as a dedicated error — the operation's outcome decides which one the user sees.

## Trusted Lists and the LOTL

eIDAS trust is anchored in the **List of Trusted Lists**, published by the European Commission and
signed with keys that rotate. DSS validates the LOTL against a bundled keystore, which OmniSign ships
at `shared/src/jvmMain/resources/lotl-keystore.p12`.

When the Commission rotates those keys, refresh it:

```bash
./gradlew :shared:updateLotlKeystore
```

The task downloads the current Official Journal keystore from the DSS demonstrations repository and
overwrites the bundled copy. Commit the result — it is a build input, not a cache.

Beyond the EU LOTL, OmniSign supports custom Trusted Lists and directly-trusted certificates. The
trust store is app-managed and content-addressed: certificates are stored as `sha256-<hex>.der` files,
deduplicated by fingerprint, and reference-counted so removing the last reference collects the file.
`FileTrustStore` implements it; the desktop, server, and CLI all share the format.

## Before you conclude DSS cannot do something

DSS's API surface is much wider than the parts OmniSign uses, and it is easy to assume a limitation
that is not there. Two capabilities OmniSign does **not** currently use, but which exist:

- `TempFileResourcesHandlerBuilder` spools PAdES output to temporary files rather than building it in
memory.
- The `dss-cms-stream` module streams CMS data instead of materialising it.

So "DSS cannot stream this" is usually false. Check
[the DSS documentation](https://ec.europa.eu/digital-building-blocks/DSS/webapp-demo/doc/dss-documentation.html)
or grep the DSS sources for `*Handler` and `*Builder` types before designing around a supposed
constraint.
