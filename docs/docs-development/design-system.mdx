# The UI design system

`composeApp` does not use Material Design. Every button, dialog, text field, and switch in OmniSign is
a **Lumo** component, defined in `composeApp/src/commonMain/.../lumo/`.

This is not a slight exaggeration: no source file in `composeApp` imports a Material 3 composable. The
artifact is on the classpath, but the only reference to `androidx.compose.material` anywhere is Lumo's
own ripple implementation.

If you are adding UI, reach for a Lumo component first. If one does not exist, add it to `lumo/` rather
than importing Material into `ui/`.

## Layout

| Path | Contents |
| --- | --- |
| `lumo/Theme.kt` | `LumoTheme` accessor and the theme composable |
| `lumo/Color.kt`, `lumo/Typography.kt` | Design tokens |
| `lumo/components/` | 20 top-level components plus `card/`, `otptextfield/`, `progressindicators/`, `snackbar/`, `textfield/`, `topbar/` — 36 files in all |
| `lumo/foundation/` | `Elevation`, `ButtonElevation`, `Ripple`, `Providers`, `SystemBarsDefaultInsets` |
| `lumo/PlatformContextMenu.kt` | `expect fun ProvidePlatformContextMenu` — Lumo-styled right-click menu on desktop, passthrough on web |

Lumo is generated and updated by the [Lumo Gradle plugin](https://github.com/nomanr/lumo-ui)
(`com.nomanr.plugin.lumo`, pinned to `1.2.5` in `gradle/libs.versions.toml`), configured through
`lumo.properties` at the repository root:

```properties
ThemeName=LumoTheme
ComponentsDir=composeApp/src/commonMain/kotlin/cz/pizavo/omnisign/lumo
PackageName=cz.pizavo.omnisign.lumo
KotlinMultiplatform=true
```

The generated sources are checked in and freely edited afterwards — treat them as ours, not as
vendored code.

## Icons

Every icon in the app is a [Tabler](https://tabler.io/icons) icon. The set lives in
`composeApp/src/commonMain/composeResources/drawable/` as 62 SVGs, stored with hard-coded `black`
strokes and fills so that Compose can recolour them at render time with `tint`.

Three are not stock Tabler: `icon_window_restore` is derived from Tabler's `copy`, and `icon_eu` and
`icon_eu_crossed` are original artwork. Tabler is MIT-licensed — see
[NOTICE.md](https://github.com/pizavo/omnisign/blob/main/NOTICE.md).

### The documentation site keeps no copies of its own

`docs/scripts/generate-icons.mjs` runs before every `start`, `build`, and `typecheck`. It reads each
drawable out of the app, rewrites the `black` fills to `currentColor` so CSS can theme them, and emits a
typed barrel. The result lands in `docs/src/icons/`, which is generated and git-ignored.

The app's `drawable/` directory is therefore the single source of truth. Change an icon there and the
docs follow on the next build — there is nothing to keep in sync by hand.

Render one with `AppIcon`:

```tsx
import AppIcon from '@site/src/components/AppIcon';

<AppIcon name="shield_check" color="success" label="Valid signature" />
```

`name` is the file stem without the `icon_` prefix. `color` is an optional semantic tint mirroring the
desktop theme; omit it to inherit the surrounding text colour. Pass `label` when the icon carries meaning
on its own — without one it is exposed to assistive technology as decorative.

:::danger[A drawable's file name is not its Tabler name]
`icon_window_minimize` is Tabler's **`minus`**. `icon_window_maximize` is Tabler's **`square`**. Tabler
*also* publishes icons called `window-minimize` and `window-maximize`, and they are different glyphs.

So never resolve an icon by guessing its Tabler name. The SVG in `drawable/` is the artwork, and it is
the only thing that records what the app actually draws. This is why the docs copy the file rather than
importing from an icon package — a name-based mapping would compile, typecheck, and render the wrong
picture.
:::

### Adding an icon

Drop `icon_<name>.svg` into `composeApp/src/commonMain/composeResources/drawable/` with `black` strokes
and fills. It becomes `Res.drawable.icon_<name>` in the app and `<AppIcon name="<name>" />` in the docs
on the next build. There is no registration step.

Icons that belong to the documentation site rather than to the app — the "Enlarge" badge on the Mermaid
diagrams, for instance — are inlined in the component that uses them. `AppIcon` exists to depict the
app's own UI, so putting site chrome in `drawable/` would ship the app a resource it never draws.

## `LumoTheme` is one of the sanctioned `object`s

[Coding conventions](conventions.mdx#dependency-injection-is-koin-exclusively) require Koin for
dependency wiring, with a short list of exemptions. `LumoTheme` is one of them:

```kotlin
object LumoTheme {
    val colors: Colors
        @ReadOnlyComposable @Composable
        get() = LocalColors.current

    val typography: Typography
        @ReadOnlyComposable @Composable
        get() = LocalTypography.current
}
```

It holds no state — it is a `@Composable` read of two CompositionLocals. Injecting it through Koin
would be meaningless, because its values change with the composition, not with the container.

The same reasoning covers the `*Defaults` objects that supply component default parameter values.

## `LocalReadOnly`

The web client renders most of the settings and profile UI in a view-only mode. Rather than threading
an `enabled` flag through every field, Lumo inputs read a `staticCompositionLocalOf`:

```kotlin
CompositionLocalProvider(LocalReadOnly provides true) { SettingsForm() }
```

Every Lumo input computes its effective state as `enabled && !LocalReadOnly.current`, so a control that
is already disabled stays disabled. Text fields, dropdowns, switches, checkboxes, and buttons grey out
while still showing their current value.

**Chips are the deliberate exception.** They keep their normal appearance and merely ignore
interaction, because a greyed-out chip reads as "this option is unavailable" rather than "this option
is selected but the form is locked".

To carve out an editable region inside a read-only subtree, provide `false` again — this is how the
Backup and Language and Region settings stay usable on web while the rest of the dialog is frozen.

## Text selection, and the dialog trap

`SelectableContent` wraps its children in a `SelectionContainer` so text can be selected and copied.
It is used in 17 places.

:::danger[Opening a dialog from inside `SelectableContent` will crash on click]
A Compose dialog renders into a **separate window layer**. When it is opened from inside a
`SelectionContainer`, it inherits that selection registrar across the layer boundary, and the first
click inside the dialog throws:

```text
IllegalStateException: layouts are not part of the same hierarchy
```

The fix is to host the dialog's content under `DisableSelection`, which clears the inherited
registrar. `CertificateDetailsDialog` does exactly this, and its KDoc records why.

To re-enable copying for a specific region inside such a dialog, nest a fresh `SelectableContent`
inside the `DisableSelection` scope — that is how the certificate detail rows stay copyable.

There is no way to detect this automatically: `LocalSelectionRegistrar` is `internal` in Compose
Multiplatform.
:::

## Platform seams

`ui/platform/` holds the `expect` declarations for everything a composable cannot do portably — PDF
rendering, file export, cursors, theme persistence, and the app locale. The desktop `actual`s are in
`jvmMain`, the browser ones in `webMain`. Window controls are the exception: `WindowControls.kt` lives
only in `commonMain` and exposes CompositionLocals (`LocalDragAreaCallback`, `LocalWindowDragModifier`)
that each host provides values into.

Two are worth knowing about because they behave differently rather than merely being implemented
twice:

- **PDF rendering** — PDFBox on desktop, MuPDF compiled to WebAssembly in the browser.
- **Saving a document** — Chromium's `showSaveFilePicker` returns the chosen name, so the app can
report where the file went. Every other browser falls back to a download, and the app reports
success without a filename.
