# Contributing

Contributions are welcome. This page covers the process; the rules your code is judged against are in
[Coding conventions](conventions.mdx).

## Pull request flow

1. Branch off `main`.
2. Make your change, with tests and KDoc.
3. Run the tests for the module you touched — see [Testing](testing.mdx).
4. Open a pull request against `main`.

CI builds and tests the affected components, and a pull request needs one approving review before it
can merge. Keep pull requests focused, and reference any related issue. Which workflows run is decided
by the paths you touched — see [Releases and CI](releases.mdx#which-ci-runs-on-your-change).

By participating you agree to the
[Code of Conduct](https://github.com/pizavo/omnisign/blob/main/CODE_OF_CONDUCT.md). Please report
security vulnerabilities privately, following the
[security policy](https://github.com/pizavo/omnisign/blob/main/SECURITY.md), rather than opening a
public issue.

## Commit messages are the release notes

Release notes are generated from commit messages with
[git-cliff](https://git-cliff.org/), so every commit **must** follow
[Conventional Commits](https://www.conventionalcommits.org):

```text
type(scope): short summary
```

The `type` decides whether the commit is published:

| Type | In the release notes? |
| --- | --- |
| `feat` | Yes, under *Features* |
| `fix` | Yes, under *Bug Fixes* |
| `perf` | Yes, under *Performance* |
| `revert` | Yes, under *Reverts* |
| Any type with `!` (`feat(cli)!:`) | Yes, under *Breaking Changes*, always first |
| `docs`, `test`, `refactor`, `style`, `chore`, `build`, `ci` | No — still welcome, just not published |
| Anything that does not parse | No |

A `BREAKING CHANGE:` footer has the same effect as `!`. `scope` is optional, lowercase, and names the
area you touched: `pkcs11`, `dss`, `cli`, `web`.

Two consequences follow from how the changelog is assembled, and both change how you should commit.

### Each commit appears individually

Pull requests are merged preserving their commits, so every commit shows up as its own bullet. Make
one clean conventional commit per logical change rather than one large one — but do not over-split
either. A dependency bump the feature *needs*, or an ignore rule for a config file it introduces,
belongs in the same commit as the feature.

### Releases are per component

There are four independently versioned components — CLI, desktop, server, and web — and a commit is
attributed to one by **the files it changes**, not by its scope.

:::warning[Anything touching `shared/` or `gradle/` lands in every component's notes]
The scope in `feat(cli): …` does not filter anything. If that commit also edits `shared/`, it appears
in the desktop, server, and web release notes too.

Keep each commit confined to the module it belongs to. When a change genuinely spans `shared/` and a
consumer, that is fine — just know it will be published four times, and write the summary so it reads
sensibly in all four.
:::

## The pull request checklist

The template asks you to confirm four things:

- Commits follow Conventional Commits.
- Tests pass for the affected components.
- KDoc is added or updated for every new or changed class, interface, and function.
- The change is focused and follows the conventions.

## Working on this documentation site

The site is [Docusaurus](https://docusaurus.io/) 3.10.1, managed with **pnpm**, and requires
**Node.js 26+**.

```bash
cd docs
pnpm install
pnpm start
```

Content lives in five directories, one per documentation section: `docs-cli`, `docs-desktop`,
`docs-server`, `docs-web`, and `docs-development`. Sidebars are **autogenerated from the directory
tree**, so adding a page adds a navigation entry — position it with `sidebar_position` in the
frontmatter.

Every page is `.mdx`, and MDX v3 syntax applies:

| Do | Not |
| --- | --- |
| `## Heading {/* #custom-id */}` | `## Heading {#custom-id}` |
| `:::note[Title]` | `:::note Title` |

:::danger[A green build does not mean the page is right]
The legacy `:::note Title` form does not error — it renders as literal paragraph text reading
`:::note Title`, with `[SUCCESS]` and zero warnings from the build. Titleless `:::note` keeps working,
which hides the problem.

After changing admonitions, verify the built output rather than trusting the build:

```bash
pnpm run build
grep -r ':::' build/ --include=*.html
```

That must find nothing.
:::

Run `pnpm run typecheck` before opening a pull request. `onBrokenLinks` is set to `throw`, so a broken
internal link fails the build — which is the one class of error you can rely on the build to catch.
