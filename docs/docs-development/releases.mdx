# Releases and CI

OmniSign releases **four components independently**: the CLI, the desktop app, the server, and the web
client. Each has its own version, its own tag series, and its own release notes, all derived from the
commit history rather than from a file anyone edits.

## Which CI runs on your change

Each component has a workflow that triggers on its own paths, and the docs have two:

| Workflow          | Runs when you touch                                                            |
|-------------------|--------------------------------------------------------------------------------|
| `ci-cli.yml`      | `cli/**`, `shared/**`, `gradle/**`, `*.gradle.kts`, `gradle.properties`        |
| `ci-desktop.yml`  | `composeApp/**`, `shared/**`, `gradle/**`, `*.gradle.kts`, `gradle.properties` |
| `ci-server.yml`   | `server/**`, `shared/**`, `gradle/**`, `*.gradle.kts`, `gradle.properties`     |
| `ci-web.yml`      | `composeApp/**`, `shared/**`, `gradle/**`, `*.gradle.kts`, `gradle.properties` |
| `ci-docs.yml`     | `docs/**`, the app's drawables, `ci-docs.yml`, `setup-docs`, in pull requests  |
| `deploy-docs.yml` | `docs/**` and any module's `src/**`, on `main`                                 |

Two facts fall out of that table, and they explain most of the surprises:

- The `shared` and `gradle` directories appear in *every* component's list. A one-line change to
`shared` builds and tests all four.
- The `composeApp` directory appears in *two* of them. Desktop and web are built from the same module.

For the four component workflows, those paths filter **pushes to `main`** only. The pull-request
trigger has *no* path filter: all five `ci-*.yml` workflows declare `pull_request: branches: [main]`
without one, plus `workflow_dispatch`, so every pull request starts all five. `ci-docs.yml` has no
push trigger, since `deploy-docs.yml` builds the site on `main`, and `deploy-docs.yml` in turn has
no pull-request trigger.

A composite action, `detect-changes`, checks the same paths at the job level, so a workflow that is
triggered can still skip its build when nothing relevant moved. `workflow_dispatch` is always relevant.
A component workflow gives the action its module, and the action adds `shared`, `gradle`, the root
build scripts, and `gradle.properties`. `ci-docs.yml` passes its own list through the action's
`paths` input instead, because the site is not part of the Gradle build. That list includes
`composeApp/src/commonMain/composeResources/drawable/`, whose SVGs `docs/scripts/generate-icons.mjs`
turns into the site's icon components.

On their Ubuntu runner, `ci-cli.yml` and `ci-desktop.yml` also build the Linux packages and install
them in `ubuntu:22.04` and `fedora:latest` containers. The CLI's are installed for real and then
run with `omnisign --version`. The desktop's are only simulated on Ubuntu and installed without
their scripts on Fedora, since those scripts register the app with a desktop menu a bare container
lacks. A dependency that does not resolve, or a directory an RPM claims from Fedora's `filesystem`
package, therefore fails the pull request instead of the release.

## Versions come from tags, not from files

Each releasable module reads its version from a Gradle property, falling back to a hardcoded default
for local builds — `1.9.0` in `cli`, `1.0.0` in `server` and `composeApp`. `shared` declares no
version at all (it stays `unspecified`, which is why the Wasm workspace version has to be pinned
separately, below):

```kotlin
version = project.findProperty("releaseVersion")?.toString() ?: "1.9.0"
```

Release workflows pass `-PreleaseVersion=<computed>` — except the Windows packaging jobs in
`release-cli.yml` and `release-desktop.yml`, which set the equivalent
`ORG_GRADLE_PROJECT_releaseVersion` environment variable instead. Nothing in the repository records
the current released version; the tag series is the source of truth.

Tags are namespaced per component, in the form `<prefix>/v<semver>`:

| Component | Tag prefix | Module path  | Example tag                                            |
|-----------|------------|--------------|--------------------------------------------------------|
| CLI       | `cli`      | `cli`        | `cli/v1.17.0`                                          |
| Desktop   | `desktop`  | `composeApp` | `desktop/v1.11.0`                                      |
| Server    | `server`   | `server`     | `server/v1.6.0`                                        |
| Web       | `web`      | `composeApp` | `web/v1.3.0`, and `web/v1.1.2-pre.2` for a pre-release |

## How the version and notes are computed

The `compute-release` composite action runs [git-cliff](https://git-cliff.org/) over the commits since
the component's latest tag, and outputs `version`, `tag`, `should_release`, and `prerelease`.

`cliff.toml` has no `[bump]` section, so git-cliff's defaults pick the next version: a breaking change
bumps the major version, a `feat` the minor version, and any other commit in the notes the patch
version. Which commit types reach the notes is listed in
[Contributing](contributing.mdx#commit-messages-are-the-release-notes). What matters here is **how the
commits are scoped to a component**. A commit belongs to a component when it changes at least one
file that matches one of the component's include paths and none of its exclude paths. The include
paths are the component's module, the shared core, and the build infrastructure:

```bash
--include-path "${MODULE_PATH}/**" \
--include-path 'shared/**' \
--include-path 'gradle/**' \
--include-path 'build.gradle.kts' \
--include-path 'settings.gradle.kts' \
--include-path 'gradle.properties'
```

The root build scripts are named one by one because git-cliff's globs let `*` cross `/`, so
`*.gradle.kts` would also match `cli/build.gradle.kts` and put one module's build change into all four
components' notes. GitHub's path filters and `detect-changes` keep `*` inside the root directory,
which is why the table above can say `*.gradle.kts`. A module's own build script is covered by its
module's include path.

Tests never ship, so every component excludes `shared`'s test source sets (`commonTest`, `jvmTest`,
`wasmJsTest`) and its own module's tests (`src/test`, or `commonTest`, `jvmTest`, and `webTest` in
`composeApp`). And since no component compiles every source set, each also excludes those it does
not:

| Component      | Also excluded                                           |
|----------------|---------------------------------------------------------|
| CLI and server | `shared/src/wasmJsMain/**`                              |
| Desktop        | `shared/src/wasmJsMain/**`, `composeApp/src/webMain/**` |
| Web            | `shared/src/jvmMain/**`, `composeApp/src/jvmMain/**`    |

:::warning[The scope in your commit message filters nothing]
A commit is attributed to a component by the paths it touches, not by `feat(cli):`. Concretely:

- A commit touching `shared/`, `gradle/`, a root build script, or `gradle.properties` appears in
**all four** components' release notes. The exceptions are `shared`'s platform source sets:
`shared/src/jvmMain/` reaches all but the web client's notes, and `shared/src/wasmJsMain/` only the
web client's.
- A commit touching `composeApp/` appears in **both** the desktop and web notes, except that
`composeApp/src/jvmMain/` reaches only the desktop's and `composeApp/src/webMain/` only the web
client's.
- A commit that touches nothing but tests, the docs, or the workflows appears in **none**.

Of the commits the paths let through, the type decides which are listed, whatever their scope. The
scope only decides where: one whose scope names another component, such as a `fix(server):` that
reaches the CLI through `shared/`, goes into a collapsed *Other Changes* section, and one whose scope
names a maintenance area, such as `fix(build):`, into a collapsed *Maintenance* section. Both still
count towards the version bump, so a `feat(server):` that reaches the CLI raises the CLI's minor
version. A `!` commit is listed under *Breaking Changes* in every component it reaches, whatever its
type, and bumps the major version of each.

The scope cannot keep a commit out of a component's notes. The only lever is keeping each commit
confined to the module it belongs to — which is why
[Contributing](contributing.mdx#releases-are-per-component) asks for it.
:::

When a release does happen, `should_release` is `true` and the rendered notes are uploaded as an
artifact, then attached to the GitHub release.

## Pre-releases

The release workflows accept four `workflow_dispatch` inputs:

| Input               | Effect                                                                                                                   |
|---------------------|--------------------------------------------------------------------------------------------------------------------------|
| `dry_run`           | Compute the version and render the notes into the job summary, then stop — nothing is tested, built, tagged, or released |
| `release_as`        | Force an explicit version instead of the computed bump                                                                   |
| `prerelease`        | Cut a pre-release, flagged as such on GitHub                                                                             |
| `prerelease_suffix` | The identifier to use, sanitized to `[A-Za-z0-9-]`; defaults to `pre`                                                    |

A pre-release series bumps from the last **stable** tag and appends a counter: `1.1.2-pre.1`,
`1.1.2-pre.2`, and so on. The action finds the highest existing counter for that target version and
increments it.

:::danger[Immutable releases burn tag names permanently]
This repository has GitHub's **immutable releases** enabled. Publishing a release reserves that tag
name in an internal ledger *forever* — it survives deleting the tag, deleting the release, and even
deleting the repository.

**Never delete a published release to "redo" it.** The `-pre.N` counter will deadlock: the action
computes the next free counter from existing *tags*, but GitHub refuses to publish the burned name,
and the tag no longer exists to push the counter past it.

If you land in this state, roll forward to `pre.(N+1)` rather than trying to reclaim the name.
:::

## Releasing all four at once

`release-all.yml` — **Release — All** in the Actions sidebar — is a launcher, not a fifth pipeline.
It dispatches the four release workflows, waits for them, and writes one summary table:

| Component | Outcome                   |
|-----------|---------------------------|
| CLI       | ✅ Released `cli/v1.20.0` |
| Desktop   | ⏭️ Nothing to release      |
| Server    | ❌ failure                |

Four checkboxes pick the components (all on by default); `dry_run`, `prerelease`, and
`prerelease_suffix` are passed through unchanged. `release_as` is deliberately **not** offered — it
forces one explicit version, which four independently versioned components cannot share. Run that
component's own workflow when you need it.

Nothing about the per-component workflows changes. Each still computes its own version, still decides
for itself whether it has anything to release, and still appears in the Actions tab as its own run
that can be inspected or re-run on its own. The launcher only reads the outcome: a run whose jobs are
all skipped apart from `Compute version & notes` had nothing to release, and the aggregate run fails
if any component's run did.

:::note[Why this needs no personal access token]
Events triggered with the built-in `GITHUB_TOKEN` normally do not create workflow runs at all —
`workflow_dispatch` and `repository_dispatch` are the two documented exceptions. So the launcher
dispatches with `github.token` and needs nothing beyond `permissions: actions: write`.
:::

## Building the artifacts

Native installers cannot be cross-compiled, so the **CLI and desktop** release workflows run a
three-OS `test` job and then fan out across three packaging runners, each building only what its OS
supports:

```bash
# linux
./gradlew :composeApp:packageDeb :composeApp:packageRpm :composeApp:createDistributable
# windows
./gradlew :composeApp:packageMsi :composeApp:packageExe :composeApp:createDistributable
# macos
./gradlew :composeApp:packageDmg :composeApp:createDistributable
```

The CLI uses its own per-format tasks (`:cli:jpackageDeb`, `:cli:jpackageWinMsi`, `:cli:jpackageDmg`,
and so on). The server and web releases each need only one Linux runner: `release-server.yml` runs
`:server:buildFatJar`, attaches `server/build/libs/*-all.jar` to the release, **and** builds
`server/Dockerfile` and pushes it to `ghcr.io/<owner>/omnisign-server`, tagged with the version plus
`latest` for non-pre-releases; `release-web.yml` runs `:composeApp:wasmJsBrowserDistribution` and
attaches the zipped `productionExecutable/` as `web-dist.zip`. See
[Building and running](building.mdx#producing-artifacts).

:::note[Why the Wasm npm package version is pinned]
`composeApp/build.gradle.kts` pins the Wasm npm workspace version to a constant:

```kotlin
val wasmNpmPackageVersion = "1.0.0"
```

Without it, `-PreleaseVersion` leaks into the generated npm `package.json`, and
`kotlinWasmStorePackageLock` fails on release builds while passing on ordinary CI for the *same*
commit. These workspace packages are internal to the build and never published, so a constant version
is safe.

Do **not** "fix" such a failure by running `kotlinWasmUpgradePackageLock` — that bakes the release
version into the committed lockfile.
:::

## Documentation

`deploy-docs.yml` builds the Dokka API reference, copies it into `docs/static/api/`, builds the
Docusaurus site, and publishes it to GitHub Pages. It runs on the pushes to `main` that
[the table above](#which-ci-runs-on-your-change) lists, and on `workflow_dispatch`.

`ci-docs.yml` checks a pull request instead. It type-checks the site with `pnpm run typecheck` and
builds it with `pnpm run build`, which fails on a broken link or anchor, so a change to the pages or
to the docs toolchain is tested before it merges. It leaves out the Dokka step, so the API reference
is built only by `deploy-docs.yml`.

Both set the toolchain up through the `setup-docs` composite action: `pnpm/action-setup` installs the
pnpm that `docs/package.json` pins (`packageManager: pnpm@12.18.0`), `actions/setup-node` installs
Node 26, which `engines.node: >=26.0` requires, and `pnpm install --frozen-lockfile` installs the
dependencies.
