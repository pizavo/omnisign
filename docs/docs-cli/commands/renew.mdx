# renew

Execute configured renewal jobs — inspects each matched PDF and performs whichever preservation step
that document actually needs, in place.

Intended to be invoked daily by the OS scheduler registered via
[`schedule install`](schedule#schedule-install), but can also be run manually at any time.

```
omnisign renew [options]
```

## What "needs renewal" means

Preservation is not one action on one clock. Each PAdES level is missing something different, and the
deadlines are not the same length — so the step a document needs, and how urgent it is, depend on
where it currently stands:

| Document is at                                        | Step                                         | Deadline                                                                  |
|-------------------------------------------------------|----------------------------------------------|---------------------------------------------------------------------------|
| **B-B / B-T** — no revocation data                    | Embed revocation data and seal (→ B-LTA)     | The **signing certificate's** expiry                                      |
| **B-LT**, revocation predates the signature timestamp | Refresh the revocation data (→ B-LT)         | The issuer's next CRL/OCSP publication                                    |
| **B-LT**, revocation sound                            | Seal it with an archival timestamp (→ B-LTA) | The earlier of the revocation's `nextUpdate` and its issuer's expiry      |
| **B-LTA**                                             | Re-timestamp (→ B-LTA)                       | The outermost timestamp's certificate expiry, or its algorithms aging out |

Only the last row is the "wait until it is nearly expiring" case, and only it uses the job's renewal
buffer. The rows above it are **due immediately**: the material they need is available now and will
not be later, so waiting only shrinks the window.

:::warning[The signing certificate is the deadline that cannot be extended]
Once a signing certificate expires, its issuer stops vouching for that certificate's revocation
status, and no acceptable revocation data for it can be obtained again — the standards forbid using
data issued after expiry, and DSS enforces that. A document still at B-T when its signing certificate
expires can therefore **never** reach B-LT. `renew` reports such a file as terminal (`[TERMINAL]`)
rather than retrying it, because no later run can succeed either.

This is why enrolling a document in a renewal job while its certificate is still valid matters, and
why a B-T document is reported as due on its first run rather than years later when some timestamp
approaches expiry.
:::

Renewal is coverage-aware at B-LTA: a timestamp already sealed by a current document timestamp does
not drive a renewal of its own, so a document is not re-timestamped on every run once one of its
inner timestamps ages.

## Options

| Option             | Description                                                            |
|--------------------|------------------------------------------------------------------------|
| `-j, --job <name>` | Run only the named renewal job. Runs all configured jobs when omitted. |
| `--dry-run`        | Report which files need renewal without modifying any file.            |

A job may decline to bring up documents that carry no long-term validation material, with
`schedule job add --no-promote` (see [`schedule job add`](schedule#schedule-job-add-options)). Such files are
then reported as skipped by policy, never silently ignored.

## Examples

```bash
# Run all renewal jobs
omnisign renew

# Dry-run to see what would be renewed
omnisign renew --dry-run

# Run a single named job
omnisign renew --job university
```

## Per-file outcomes

| Tag           | Meaning                                                                                 |
|---------------|-----------------------------------------------------------------------------------------|
| `[PROMOTED]`  | The document reached a level it had not held before                                     |
| `[REFRESHED]` | Stale revocation data was replaced; the document is at B-LT and will be sealed next run |
| `[RENEWED]`   | Existing B-LTA protection was re-timestamped                                            |
| `[SKIP]`      | Nothing was due, or the job declines this document's step                               |
| `[TERMINAL]`  | The deadline has passed — reported once, then left alone                                |
| `[ERROR]`     | The step failed; **the original file is left untouched**                                |

A renewal only overwrites a file once the output is confirmed to have delivered: the extension must
report that it embedded the revocation data the target level needs, and the level read back out of
the produced bytes must have reached that target. A level that cannot be established counts as not
confirmed. Otherwise the original stays as it was and the run reports an error — replacing an archive
with a weaker document would also reset the renewal clock, hiding the gap until the new timestamp
itself ages.

Terminal files are counted separately from errors, and do not make a run unsuccessful. Nothing
failed, and treating them as failures would leave the run permanently reporting itself as broken over
something no run can fix — including the staleness warning, which would then never clear.

## When the timestamp server is down

Reaching the TSA is the last thing an extension does, so every document first parses the archive and
collects revocation data before the timestamp call can fail — and if the server is unreachable, it
then waits out the full connection timeout. Against a large backlog that is hours of work that renews
nothing.

A run therefore stops calling a timestamp server after **three consecutive documents** fail against
it, and reports the rest immediately:

```
[ERROR] /archive/e.pdf — the timestamp server https://tsa.example.com could not be reached
        on the last 3 attempts, so this run stopped calling it; the original was left
        unchanged and the next run will try again
```

Only failures that would repeat count towards those three — the server could not be reached, or it
answered with something that is not a timestamp token. A server that answers and *rejects* a request
(an RFC 3161 `PKIFailureInfo`) says nothing about the next document, so it never stops the run, and
any document that does get timestamped resets the count. The message names which of the two it was,
because they call for opposite responses: an outage is waited out, while an endpoint that answers
without producing a timestamp is usually a URL that does not point at an RFC 3161 service.

The skipped documents are reported as errors, not as skips. They are retried in full on the next run.

## When a new timestamp would not last

At B-LTA, a re-timestamp is only worth keeping if it moves the document's deadline later. A timestamp
server whose certificate expires within the renewal buffer, or whose signing key or algorithms stop
being acceptable within it, issues timestamps that are due for renewal the moment they are made. Under
the default policy of DSS 6.5.1 this includes any server that signs with a 2048-bit RSA key: such keys
are accepted until 1 January 2027, so with the default 90-day buffer their timestamps have been due on
issue since 3 October 2026.

Renewing a document through such a server again would add a timestamp that ages out no later than the
one it covers, so every run would grow the file and gain nothing. Each renewed document is therefore
assessed again before it replaces the original, and a re-timestamp whose new deadline is no later than
the document's current one is refused:

```
[ERROR] /archive/a.pdf — the new timestamp would be due for renewal by 2027-01-01T00:00:00Z, no later
        than the document's current deadline (2027-01-01T00:00:00Z): the timestamps from the timestamp
        server https://tsa.example.com rely on an algorithm or key size that stops being acceptable
        within the 90-day renewal buffer, so renewing through it cannot extend the protection; the
        original was left unchanged
```

Once a job has received such a timestamp, it stops calling the server for the rest of the run for the
documents it cannot help, those whose deadline is no earlier, and reports them as errors straight
away, like the documents passed over when a server is down.

A re-timestamp that does reach further is kept, and so is a promotion, since it adds revocation data
or a seal the document lacked. When the new timestamp is itself already due, though, the result
carries a warning saying so, because the next run will not be able to extend it through the same
server. The remedy is the same in every case: point the job at a timestamp server whose certificate
and signing key outlast the renewal buffer.

## OS notifications

When a renewal job has notifications enabled (the default), OmniSign fires an OS desktop
notification after the job completes:

- **Success** — `"N file(s) successfully re-timestamped."`
- **Partial failure** — `"N re-timestamped, M error(s)."`
- **Full failure** — `"N file(s) could not be re-timestamped. Digital continuity may be at risk."`
- **Terminal documents** — raised alongside the outcome above when a run finds documents whose
  deadline has passed. Only *newly* terminal documents are announced; a file already reported is not
  announced again, since the condition cannot be acted on and cannot change.

Two further notifications are run-wide rather than per-job, so they ignore the per-job opt-in:

- **Renewal has stalled** — no run has succeeded for the configured number of days (14 by default).
- **Runs keep being interrupted** — three runs in a row were stopped before they could finish, which
  a restart or a shutdown landing on the scheduled time will do. A single interruption is not
  announced; the next run normally completes and nothing is wrong. Raised once per streak rather than
  nightly, the standing signal being `schedule status` and, on the desktop, a badge on the settings
  button.

:::note[Why an interrupted run is announced from the *next* run]
A process that is killed executes no further code, so it cannot report its own death — no run record,
no notification, no log entry is written. The following run is the first thing able to notice, which
is also why the count needs a few days to build up. On a machine that was switched off at the
scheduled time the catch-up run fires shortly after boot, so the notification arrives while you are
at the computer.
:::

Disable notifications per job with `schedule job add --no-notify` (recommended for headless
server deployments).

## JSON output

Pass `--json` (the global flag) to get machine-readable output:

```bash
omnisign --json renew
```

Returns a JSON object with `success`, `checked`, `renewed`, `skipped`, `errors`, `unrecoverable`,
`dryRun`, `jobs` and an optional `error`. Each per-file entry in `jobs` carries `path`, `status`,
`message`, `warnings`, and a `reason` naming the preservation gap it relates to (`BELOW_LT`,
`LT_REFRESH_NEEDED`, `LT_NOT_SEALED`, `TIMESTAMP_EXPIRING`, `ALGORITHM_WEAKENING`).
